Deep dive
There are three ways to run Langflow and the right one depends on who you are. The uv Python package is the recommended path for anyone comfortable with a terminal: uv is a fast package manager that creates clean virtual environments, and installing into an isolated environment is not optional advice - Langflow pulls in a large dependency tree, and mixing it into a shared environment is the most reliable way to create version conflicts that are painful to unwind. Langflow Desktop is a bundled application for Windows and macOS that hides the command line entirely; it is ideal for non-technical teammates or quick prototyping, at the cost of less control over versions and configuration. Docker is the third route and the one to choose for a reproducible, isolated server deployment. Whichever you pick, the first run does real work: it creates a local SQLite database to store your flows, scans and registers every component (models, tools, vector stores), and starts a web server on port 7860. Understanding that sequence explains the common failure modes - a missing Python version stops it before it starts, a process already on port 7860 blocks the server, and on some Linux systems missing build tools break a dependency's compilation. Each has a known fix, below.

LF1 What is Langflow? Langflow Orientation
Langflow is an open-source visual builder for LLM applications. You drag components onto a canvas, wire them together, and it becomes a runnable flow - and then a REST API. It's the fastest way to prototype a RAG pipeline or agent without writing plumbing code.
Why this matters — use case
You need to show a working refund-policy assistant to stakeholders by Friday. Langflow lets you assemble retrieval + prompt + model visually in an afternoon, test it in the built-in playground, and expose it as an API - no scaffolding code.
What's in this section
  • Langflow is a visual, node-based canvas for building LLM workflows - drag, connect, run
  • Every flow is backed by real Python components, so what you build visually maps to actual code
  • It ships a component library: models, embeddings, vector stores, loaders, agents, tools
  • Flows export as REST API endpoints or MCP servers, so a prototype can become a service
  • Best for prototyping, demos, and letting non-specialists assemble pipelines; hand-written code still wins for complex custom logic
Install / key command
$ pip install langflow
Concept diagram
Deep dive
Langflow sits on top of LangChain and LangGraph. When you drop a component on the canvas, you are instantiating a Python class that wraps a LangChain runnable; the edges you draw become the composition between those runnables. This is why 'visual' and 'code' are not two separate worlds here - the canvas is a graph editor for an object graph that already exists. Two consequences follow. First, anything LangChain can do, a custom component can do, because a component is just Python with typed inputs and outputs. Second, the flow's JSON is a full serialization of that graph, so it is diffable, reviewable, and portable across environments. The limitation is the flip side of the same coin: a visual graph expresses data flow well but control flow poorly. Loops, complex conditionals, and stateful branching are awkward on a canvas and are exactly where you drop to LangGraph in code.
python lf1_what_is_langflow.py
# Langflow is a visual tool, but understanding the layers underneath it
# is what lets you reason about performance, cost, and failure.

# ---------------------------------------------------------------------------
# LAYER 1  -  what you manipulate on the canvas
# ---------------------------------------------------------------------------
#   [Chat Input] -> [Prompt Template] -> [Model] -> [Chat Output]
#    each box  = a Component (a Python class)
#    each edge = a typed data connection between component ports

# ---------------------------------------------------------------------------
# LAYER 2  -  what a component actually is
# ---------------------------------------------------------------------------
from langflow.custom import Component
from langflow.io import MessageTextInput, Output
from langflow.schema.message import Message


class GreetComponent(Component):
    """A minimal custom component - this is what every canvas box really is."""
    display_name = "Greeter"
    description = "Prepends a greeting; shows the shape of a component."

    # typed INPUT ports -> these become the little dots on the left
    inputs = [
        MessageTextInput(name="text", display_name="Text", required=True),
    ]
    # typed OUTPUT ports -> the dots on the right
    outputs = [
        Output(display_name="Message", name="message", method="build"),
    ]

    def build(self) -> Message:
        return Message(text=f"Hello - {self.text}")


# ---------------------------------------------------------------------------
# LAYER 3  -  the flow as portable JSON (diff it, review it, deploy it)
# ---------------------------------------------------------------------------
FLOW_JSON = {
    "nodes": [
        {"id": "ChatInput-1",  "type": "ChatInput"},
        {"id": "Prompt-1",     "type": "PromptTemplate"},
        {"id": "Model-1",      "type": "LanguageModelComponent"},
        {"id": "ChatOutput-1", "type": "ChatOutput"},
    ],
    "edges": [
        {"source": "ChatInput-1", "target": "Prompt-1"},
        {"source": "Prompt-1",    "target": "Model-1"},
        {"source": "Model-1",     "target": "ChatOutput-1"},
    ],
}

# ---------------------------------------------------------------------------
# DECISION  -  Langflow vs hand-written code
# ---------------------------------------------------------------------------
def should_use_langflow(exploring, non_coders, complex_control_flow):
    if complex_control_flow and not non_coders:
        return "code (LangGraph): loops/branching are awkward on a canvas"
    if exploring or non_coders:
        return "Langflow: fastest path, accessible to non-specialists"
    return "Langflow to prototype, then port the stable path to code"
⚑ Real-world scenario
A team built an impressive refund-assistant demo in Langflow in two days and promised production in one week. In production it failed under load: no retry on transient model errors, no timeout on the vector store, and an unbounded agent that occasionally looped and ran up cost. None of this was visible in the happy-path demo. The fix was not to abandon Langflow but to treat the prototype as a specification: they exported the flow JSON, identified the three components that needed hardening, and re-implemented the critical path in LangGraph with explicit retries, timeouts, and a step cap - while keeping the Langflow version as the living documentation of intended behaviour.
Check your understanding
Q1What problem does Langflow actually solve?
Idea for a pipeline→Normally: write glue→Langflow: drag + wire→Runnable in minutes
💡 Skip the plumbing
It removes the boilerplate between an idea and a working LLM pipeline. Normally you'd write loaders, wire an embedder to a vector store, build a prompt template, and hook up a model - all glue code. Langflow gives you those as pre-built components you connect visually, so you get to a testable pipeline in minutes instead of hours. The tradeoff is less control than hand-written code.
Q2Is a Langflow flow 'real' code underneath?
Canvas node→Backed by component→Component is Python→Exports to JSON/API
💡 Visual maps to Python
Yes - each visual component is a real Python class with typed inputs and outputs, so the canvas is a view over an actual object graph, not a simulation. Flows serialise to JSON that you can version-control, and they can be exposed as REST endpoints. This matters because it means a Langflow prototype isn't throwaway - it's a running system you can inspect and deploy.
Q3When should you NOT use Langflow?
Heavy branching→Custom algorithms→Rigorous testing→Write it in code
💡 Complex logic wants code
When the logic outgrows what a visual graph expresses cleanly - deep conditional branching, custom algorithms, or anything needing rigorous unit testing and code review. Visual flows are excellent for assembly but awkward for intricate control flow, and they're harder to diff and test than plain Python. Use Langflow to prototype and explore, then port to code when the logic hardens.
⚠ Common pitfall
Treating a Langflow prototype as production-ready without review. Visual assembly hides details like error handling, retries, and cost controls - a flow that demos beautifully can be fragile under real traffic. Prototype in Langflow, then harden deliberately.

LF2 Anatomy of a Flow Langflow Core concepts
A flow is a directed graph of components. Each component has typed input and output ports; edges connect a compatible output to an input. Understanding ports and types is what stops the canvas feeling like guesswork - connections only work when types match.
Why this matters — use case
You drag a Vector Store onto the canvas but its output won't connect to your Prompt. Understanding that the store emits Data while the prompt expects Text tells you exactly which component is missing between them - a parser.
What's in this section
  • Components are the nodes: models, prompts, loaders, vector stores, agents, tools, outputs
  • Ports are typed - Message, Data, Text, Embeddings - and edges only connect compatible types
  • A type mismatch is the most common reason a connection 'won't stick' on the canvas
  • Component parameters (model name, temperature, chunk size) are set in the node's own panel
  • Flows must terminate in an output component; a dangling branch simply won't produce anything
Install / key command
$ pip install langflow
Concept diagram
Deep dive
The type system is the single most important thing to internalise about Langflow, because almost every 'it won't connect' or 'it connected but gave garbage' problem is a type problem in disguise. The core types you meet are Message (a chat message with role and content), Text (a plain string), Data (a structured record, or list of records, each typically carrying a .text field plus arbitrary metadata), and DataFrame (tabular). The subtle trap is that Message, Text, and Data are partially interconvertible, so an edge may be *accepted* while still being *wrong*: a Data object coerced to Text stringifies the whole record - metadata, IDs and all - and silently pollutes your prompt. So there are two failure modes, not one: the loud failure where the edge is rejected because types are incompatible, and the quiet failure where the edge is accepted but the coercion is not what you intended. Reading the port types and inspecting the actual value a component emits is how you catch both.
python lf2_flow_anatomy.py
# Ports are typed. Types are what make an edge valid - or silently wrong.

# ---------------------------------------------------------------------------
# The core port types you will actually meet
# ---------------------------------------------------------------------------
PORT_TYPES = {
    "Message":   "chat message: role + content; what Chat Input/Output speak",
    "Text":      "a plain string",
    "Data":      "structured record(s): .text + arbitrary metadata",
    "DataFrame": "tabular data (rows/columns)",
    "Embeddings":"a handle to an embedding MODEL (not vectors)",
    "LanguageModel": "a handle to a chat model, passed INTO other components",
}

# ---------------------------------------------------------------------------
# FAILURE MODE 1 - loud: incompatible types, edge REJECTED
# ---------------------------------------------------------------------------
#   [Vector Store] --Data--> X --Text--> [Prompt]
#   Data is not Text  ->  Langflow refuses the edge.
#   Fix: insert a converter.
#   [Vector Store] --Data--> [Parser] --Text--> [Prompt]     valid

# ---------------------------------------------------------------------------
# FAILURE MODE 2 - quiet: edge ACCEPTED but coercion is wrong
# ---------------------------------------------------------------------------
# A Data record stringified whole looks like this in your prompt:
BAD_CONTEXT = (
    "{'text': 'Refunds take 5-7 days', 'score': 0.83, "
    "'id': 'chunk_04', 'source': 'policy.pdf', 'page': 3}"
)
# The model now sees scores and IDs as if they were content. Garbage in.

# A Parser that emits ONLY the text (with a source label) fixes it:
GOOD_CONTEXT = "Refunds take 5-7 days.\n(Source: policy.pdf, p.3)"

# ---------------------------------------------------------------------------
# Rules that keep a flow valid AND correct
# ---------------------------------------------------------------------------
RULES = [
    "every flow needs at least one input and one output component",
    "edges require compatible port types (mode 1 is caught for you)",
    "an accepted edge is NOT proof the data is shaped correctly (mode 2)",
    "always inspect a component's runtime OUTPUT, not just its wiring",
    "a required input left empty means the component never runs",
]

# ---------------------------------------------------------------------------
# The diagnostic habit
# ---------------------------------------------------------------------------
def diagnose_bad_connection(edge_drew: bool, output_looks_right: bool) -> str:
    if not edge_drew:
        return "TYPE MISMATCH -> insert a converter (Parser / Data-to-Text)"
    if not output_looks_right:
        return "WRONG COERCION -> Parser to extract just the fields you want"
    return "wiring and shape both fine"
⚑ Real-world scenario
An engineer wired a Vector Store directly into a Prompt and the flow ran without error, but answers were bizarre - full of stray numbers and field names. Inspecting the prompt component's input revealed the cause: the retrieved Data records were being stringified whole, so the model was reading raw JSON-like dumps that included similarity scores, chunk IDs, and metadata alongside the actual text. The prompt looked fine on the canvas; only the runtime value showed the problem. Inserting a Parser configured to emit just each record's .text field - joined with separators and optional source labels - fixed it. The lesson: an edge drawing successfully tells you the types were compatible, not that the data is shaped the way your prompt expects.
Check your understanding
Q1Why won't two components connect on the canvas?
Output port type→Input port type→Mismatch = rejected→Insert a converter
💡 Types must match
Because ports are typed and Langflow only allows edges between compatible types. If a Vector Store emits Data but a Prompt expects Text, the edge is rejected - not a bug, a type check. The fix is to insert a converting component (like a Parser) that takes Data in and emits Text out. Reading the port types is the fastest way to diagnose a stuck connection.
Q2What does a component actually contain?
Typed inputs→Typed outputs→Config parameters→Runs as Python
💡 Ports plus parameters
A component has typed input ports, typed output ports, and its own configuration parameters - a model component has a model-name and temperature setting, a splitter has chunk size and overlap. The ports define how it wires into the graph; the parameters define how it behaves when it runs. Both matter: correct wiring with wrong parameters still produces bad results.
Q3Why might a flow run but produce nothing?
Component runs→Output not connected→Dead branch→No result emitted
💡 Branch never reaches output
Usually because the branch you're testing doesn't terminate in an output component, so its result has nowhere to go. Langflow executes the graph toward outputs, so a dangling chain produces no visible result even though its components are configured correctly. Check that every path you care about ends in a Chat Output or equivalent sink.
⚠ Common pitfall
Assuming a connection is correct because the line drew on the canvas. An edge can be type-valid but semantically wrong - passing raw retrieved Data where you meant formatted context. Always run the component and inspect its actual output, don't trust the wiring visually.

LF3 Your First Flow Langflow Hands-on
The simplest useful flow: Chat Input to Prompt Template to Model to Chat Output. Four components, three edges. Building it teaches the whole interaction model - placing nodes, setting parameters, wiring ports, and running it in the playground.
Why this matters — use case
Before building anything complex, get one round-trip working: type a question, see an answer. This four-node flow is the 'hello world' that proves your model credentials, your wiring, and your playground all work.
What's in this section
  • Start Langflow with 'langflow run' and open the canvas in your browser
  • Drag four components: Chat Input, Prompt Template, a Model, and Chat Output
  • Set your model credentials in the model component (or globally in provider settings)
  • Wire input to prompt to model to output, then open the Playground to test it live
  • Use the prompt template's variables to inject the user's question into your instructions

Deep dive
The four-node flow is worth dwelling on because it makes the whole execution model concrete. Langflow executes lazily and backward from the output: when you press run, it asks the Chat Output what it needs, which asks the Model, which asks the Prompt, which asks the Chat Input - then data flows forward. This is why a component with an unfilled required input simply never runs rather than erroring loudly, and why a branch that doesn't reach an output produces nothing. The Prompt Template deserves special attention: the {variable} syntax is not cosmetic. Each brace-delimited name becomes a real input port, which is how the user's typed question is injected into your instructions. Miss the variable and the prompt is static; the user's input has nowhere to flow and every answer is identical. Temperature is the other lever worth understanding rather than copying: 0 makes the model near-deterministic (it takes the highest-probability token each step), which is what you want for factual policy lookup where the same question must yield the same answer; you raise it only when variety is a feature, not a bug.
python lf3_first_flow.py
# The four-node "hello world". Small, but it teaches the whole execution model.
#
#   [Chat Input] --> [Prompt Template] --> [Model] --> [Chat Output]
#
# Langflow runs BACKWARD from the output (lazy pull), then data flows forward.

# ---------------------------------------------------------------------------
# 1. Chat Input   - captures the user's message in the Playground
#                   emits: Message   (no parameters)

# ---------------------------------------------------------------------------
# 2. Prompt Template  - the {question} variable is the crucial part
# ---------------------------------------------------------------------------
PROMPT_TEMPLATE = """You are a refund policy assistant for an enterprise SaaS product.
Answer clearly and concisely. If you are unsure, say so rather than guessing.

Question: {question}"""
#   {question}  ->  becomes a REAL input port; wire Chat Input into it.
#   No variable ->  static prompt; the user's text never reaches the model.
#   emits: Text

# ---------------------------------------------------------------------------
# 3. Model  - parameters that matter for a policy assistant
# ---------------------------------------------------------------------------
MODEL_PARAMS = {
    "provider":    "OpenAI",          # or Anthropic, Google, a local Ollama model
    "model_name":  "gpt-4o-mini",     # small + cheap is plenty for lookup
    "temperature": 0,                 # deterministic: same question -> same answer
    "max_tokens":  512,               # cap output length (and cost)
}
#   temperature 0  -> near-deterministic; correct default for factual lookup
#   temperature >0 -> variety; only when that is a feature
#   emits: Message

# ---------------------------------------------------------------------------
# 4. Chat Output  - terminal node; without it the flow shows nothing
# ---------------------------------------------------------------------------

# ---------------------------------------------------------------------------
# Testing habit: use the Playground's node inspector
# ---------------------------------------------------------------------------
CHECKLIST = [
    "type a question in the Playground",
    "click the Model node -> read the EXACT prompt it received",
    "confirm your question actually appears inside that prompt",
    "if it doesn't, your Prompt Template is missing the {question} variable",
]

# Why credentials belong in global settings, not one component:
#   set them per-component and a SECOND model node fails with an auth error
#   set them once in provider settings and every component inherits them
⚑ Real-world scenario
A newcomer's first flow returned the same generic answer no matter what they typed. They assumed the model was broken. The real cause: the Prompt Template contained the instruction text but no {question} variable, so Chat Input was wired to a port that didn't exist in any meaningful way and the user's text never reached the model. Adding {question} to the template created the input port, they wired Chat Input into it, and the flow came alive. It is the single most common first-flow mistake, and the Playground's node inspector is what reveals it: clicking the Model node showed the prompt it received never contained the user's words.
Check your understanding
Q1Why does the Prompt Template need a variable?
Write {question}→Port appears→Wire input to it→User text flows in
💡 Variable becomes a port
Declaring a {variable} in the template text makes Langflow create a matching input port on that component. That's how the user's typed question gets injected into your instructions - you wire Chat Input into the {question} port. Without a variable, the prompt is static and the user's input has nowhere to go, so the model answers the same thing every time.
Q2What is the Playground for?
Build the flow→Open Playground→Type a question→See it run live
💡 Test without leaving the canvas
It's the built-in chat interface for testing the flow you just built, without deploying anything or writing a client. You type a message, it runs through your graph, and you see the result. Crucially you can then click individual nodes to inspect exactly what each one received and returned - which is the fastest way to find where a flow is going wrong.
Q3Why set temperature to 0 for this assistant?
Policy question→Same answer expected→Temp 0 = repeatable→Consistent output
💡 Policy answers need consistency
Because a policy assistant should give the same answer to the same question - consistency matters more than variety. Temperature 0 removes sampling randomness so the response is repeatable, which makes the flow easier to test and trust. For a creative or brainstorming flow you'd raise it, but for factual lookup over a fixed policy, determinism is the right default.
⚠ Common pitfall
Setting API credentials in one model component and assuming they apply everywhere. Each model component can carry its own credentials, so a second model node may silently fail with an auth error. Prefer configuring providers globally so every component inherits the same setup.

LF4 Building a RAG Flow Langflow RAG
A RAG flow has two halves: an ingestion path that loads, splits, embeds, and stores documents, and a query path that embeds the question, retrieves matching chunks, and feeds them to the model. Langflow makes both visible on one canvas.
Why this matters — use case
To ground your refund assistant in the actual policy PDF, you build an ingestion path once to index the document, then a query path that retrieves the relevant clauses per question - so answers cite real policy instead of model memory.
What's in this section
  • Ingestion path: File loader to Text Splitter to Embedding model to Vector Store (run once per document)
  • Query path: Chat Input to Embedding to Vector Store search to Parser to Prompt to Model to Output
  • Both paths share the SAME embedding model - mismatched embedders make retrieval meaningless
  • The Parser converts retrieved Data into Text your prompt template can interpolate
  • Chunk size and overlap live on the splitter; top-k lives on the vector store search component
Install / key command
$ pip install langflow
Concept diagram
Deep dive
A RAG flow is really two independent programs that share one artifact: the vector store. The ingestion path (load, split, embed, write) is a batch job you run when documents change. The query path (embed question, search, parse, prompt, generate) runs on every user turn. Keeping them mentally separate prevents the most common RAG bugs. Three parameters do most of the work. Chunk size and overlap on the splitter control what a 'unit of retrieval' is: too large and each chunk dilutes the relevant sentence with noise; too small and you sever a clause from the heading that gives it meaning. Top-k on the search controls recall versus prompt budget: too low and the right chunk never makes it into context; too high and you flood the prompt with marginal chunks that push the model toward the wrong ones. And the embedding model must be identical on both paths - embeddings are only comparable within one model's vector space, so indexing with model A and querying with model B produces distances that are mathematically meaningless even though the flow runs without error. That silent-failure property is what makes it dangerous: nothing crashes, retrieval just quietly returns noise.

LF5 Agents & Tools in Langflow Langflow Agents
An Agent component takes a model, a set of tools, and an instruction, then decides at runtime which tools to call. Any flow can be exposed as a tool, so agents can orchestrate the retrieval pipelines you already built.
Why this matters — use case
Your assistant needs to both answer policy questions AND look up a specific customer's refund status. An agent with two tools - a retrieval tool and an API lookup tool - decides which to use based on what the user asks.
What's in this section
  • The Agent component wires together: a model, a tool list, and system instructions
  • Tools are components marked as 'tool mode' - including entire sub-flows
  • The agent decides at runtime which tool to call, unlike a fixed chain that always runs the same path
  • Tool descriptions matter enormously - the agent picks tools by reading their descriptions
  • Set a max-iterations bound so a confused agent can't loop indefinitely

Concept diagram
Deep dive
The difference between a chain and an agent is who decides the next step. In a chain, you decide at build time: retrieve, then prompt, then generate, always in that order. In an agent, the model decides at run time which tool to call, in what order, and when to stop. That runtime autonomy is powerful and is also the source of every agent failure mode, so it has to be bounded deliberately. Three controls matter most. Tool descriptions are the first, because the agent selects tools purely by reading them - a description is functionally part of the prompt, and a vague one ('gets data') causes the agent to pick the wrong tool or skip the right one. Second is the iteration cap: an agent decides for itself when it is done, so without a max-iterations bound a confused agent can loop indefinitely, burning cost and latency with no answer. Third is the tool surface itself: every tool you expose is something the agent can do, so a tool that writes or deletes needs guarding in a way a read-only search tool does not. A useful mental model is that an agent is a for-loop the model controls; your job is to make sure that loop always terminates and can only reach into safe places.

import requests

# Every flow is already a REST endpoint. Going to production is mostly about
# the things the Playground did for you silently: sessions, auth, limits.

BASE_URL = "http://localhost:7860"
FLOW_ID  = "your-flow-id"
API_KEY  = "your-langflow-api-key"     # from Settings -> API Keys


# ===========================================================================
# 1. A single call - note the session_id for conversation memory
# ===========================================================================
def call_flow(message: str, session_id: str | None = None,
              timeout: int = 60) -> dict:
    """Call a flow over HTTP the way a real client would."""
    payload = {
        "input_value": message,
        "output_type": "chat",
        "input_type":  "chat",
    }
    if session_id:
        payload["session_id"] = session_id   # WITHOUT this, every call is stateless

    resp = requests.post(
        f"{BASE_URL}/api/v1/run/{FLOW_ID}",
        json=payload,
        headers={"x-api-key": API_KEY, "Content-Type": "application/json"},
        timeout=timeout,                     # never call an LLM endpoint untimed
    )
    resp.raise_for_status()
    return resp.json()


# ===========================================================================
# 2. Multi-turn: a stable session_id threads the conversation
# ===========================================================================
def conversation_example():
    sid = "user-4821-thread-1"            # stable per user conversation
    call_flow("How long do enterprise refunds take?", session_id=sid)
    # the memory component now has turn 1; the follow-up resolves "that":
    return call_flow("And is that in business days?", session_id=sid)


# ===========================================================================
# 3. Per-request overrides with tweaks (no flow edit needed)
# ===========================================================================
def call_with_tweaks(message: str) -> dict:
    payload = {
        "input_value": message,
        "output_type": "chat",
        "input_type":  "chat",
        "tweaks": {
            "LanguageModelComponent-1": {"temperature": 0.7},  # more variety, this call only
            "VectorStore-1":            {"top_k": 8},           # broader retrieval, this call only
        },
    }
    return requests.post(
        f"{BASE_URL}/api/v1/run/{FLOW_ID}",
        json=payload, headers={"x-api-key": API_KEY}, timeout=60,
    ).json()

A trace is one end-to-end request. Inside it, every operation is a run — nested to form a tree. Understanding this parent/child structure is what lets you read a complex agent execution and pinpoint exactly which step went wrong.

  • Runs nest into a tree: a parent agent run contains child tool and model runs
  • Each run records inputs, outputs, start/end time, token counts, cost, and any error
  • Run types (llm, tool, chain, retriever) let you filter to just the operations you care about
  • Metadata and tags on runs make traces searchable — attach user id, feature, or version

A trace is one end-to-end request; a run is one operation inside it; runs nest into a tree. That structure is not decoration - it is the thing that makes debugging tractable. LS5 Evaluators & Experiments LangSmith Evaluation
An experiment runs your application over a dataset and scores each output with evaluators. Evaluators can be simple code checks, LLM-as-judge graders, or human review — and comparing two experiments is what turns 'I think this prompt is better' into evidence.
Why this matters — use case
You rewrite the RAG prompt and believe it's an improvement. Running both versions against the same dataset shows the new one scores higher on correctness but regressed on two examples — so you fix those before shipping.
What's in this section
  • An experiment = your app + a dataset + one or more evaluators, run end to end
  • Code evaluators are deterministic and cheap — exact match, contains, JSON validity, latency
  • LLM-as-judge evaluators grade subjective qualities like correctness, tone, or faithfulness
  • Compare experiments side by side: aggregate pass rate plus per-example differences
  • Calibrate LLM judges against human judgement before trusting their scores

Deep dive
An experiment runs your application over a dataset and scores each output with one or more evaluators, and comparing two experiments is what turns 'I think this is better' into evidence. The craft is in choosing the right evaluator for each criterion. Code evaluators are deterministic, free, and fast - use them whenever the check is objective: valid JSON, contains a required field, latency under a threshold, mentions a required entity. LLM-as-judge evaluators handle the subjective qualities no simple rule captures - correctness of meaning, tone, faithfulness to the provided context - at the cost of a model call per example and the need for calibration. Calibration is the step people skip and regret: an uncalibrated judge produces confident numbers that may encode its own biases rather than real quality, so you optimise toward the judge instead of toward good answers. You calibrate by checking judge scores against human ratings on a sample and tuning the grading prompt until they broadly agree. The final discipline is reading the per-example diff, not just the aggregate. A change that raises the average can still break specific cases that previously worked - fix five, break two, average still up - and only the per-example view surfaces the newly-failing cases before they ship.

from langsmith.evaluation import evaluate

# turns "I think v2 is better" into evidence.

# The target: runs your app on ONE dataset example
# ---------------------------------------------------------------------------
def target(inputs: dict) -> dict:
    return {"answer": answer_refund_question(inputs["question"])}

# ---------------------------------------------------------------------------
# Evaluator 1 - CODE check: objective, deterministic, free
# ---------------------------------------------------------------------------
def states_timeframe(run, example) -> dict:
    """Does the answer actually state a time window? A rule, not a judgment."""
    text = (run.outputs or {}).get("answer", "").lower()
    hit = any(w in text for w in ("business day", "hours", "days", "weeks"))
    return {"key": "states_timeframe", "score": 1 if hit else 0}

# ---------------------------------------------------------------------------
# Evaluator 2 - LLM-AS-JUDGE: subjective, costs a call, needs calibration
# ---------------------------------------------------------------------------
judge = ChatOpenAI(model="gpt-4o", temperature=0)

def correctness(run, example) -> dict:
    """Grade the answer against the reference for MEANING, not wording."""
    prompt = (
        "You are grading a refund assistant. Score 1 if the ANSWER matches the "
        "REFERENCE in meaning (wording may differ), else 0. Reply with only 0 or 1.\n\n"
        f"QUESTION:  {example.inputs['question']}\n"
        f"REFERENCE: {example.outputs['answer']}\n"
        f"ANSWER:    {(run.outputs or {}).get('answer', '')}"
    )
    verdict = judge.invoke(prompt).content.strip()
    return {"key": "correctness", "score": 1 if verdict.startswith("1") else 0}

# ---------------------------------------------------------------------------

    target,
    data="refund-qa-v1",

    metadata={"prompt_version": "v2"},

Deep dive
This is the single most useful skill the two tools give you together, so it is worth making the method explicit rather than implicit. The principle is that a bad final answer is a symptom, and the cause is the first run in the trace tree whose output is already wrong; every step after it inherits the error. So the method is: start from the symptom (find the exact failing trace), walk the tree top-down, find the earliest run whose output is incorrect, and fix the component responsible for THAT run - not the last step that visibly failed. The reason this matters so much is that the last visible failure is usually generation, and generation is usually innocent: the model answered faithfully from bad input handed to it upstream. If you fix the symptom you rewrite a prompt that was never wrong and the bug persists. Once you have identified the responsible component, you fix it in Langflow, then - and this is the step people rush past - you re-run the exact same failing input and read the NEW trace to confirm the intermediate output is now correct, not just that the final answer happens to look better. A plausible fix is not a verified fix. Finally you capture the case in the dataset so the fix is protected against future regressions. Symptom, root cause, verified fix, permanent guard: four steps, and skipping any of them is where debugging goes wrong.

Deep dive
The capstone question - Langflow or code, observability now or later - has a single organising principle: match the tooling to the stage you are actually at, not the stage you aspire to. Two factors decide the build tool. First, the complexity of the control flow: visual graphs express data flow well but handle deep branching, loops, and custom algorithms poorly, so intricate logic wants code (LangGraph). Second, who builds and edits it: Langflow's visual model lowers the barrier for non-specialists dramatically, which can outweigh other considerations on a mixed team. The honest answer for most projects is a progression rather than a choice - prototype visually in Langflow to find the design fast, then port the stabilised critical path to code for testing, version control, and fine control, and keep the Langflow version as living documentation. Observability follows a similar stage logic but with a stronger default: it is strictly optional while prototyping, yet turning it on from day one costs almost nothing and saves hours the first time something behaves unexpectedly. The deeper argument is about habit - teams that add observability only when production forces it arrive at their highest-stakes moment with no baseline, no dataset, and no experience reading traces. In production, observability is not optional: traces, a dataset built from real failures, experiments gating every change, and online evaluation with an owned alert are the baseline, not a maturity milestone to reach later.
python tg3_choosing_setup.py
from dataclasses import dataclass

# The capstone principle: match tooling to the stage you're actually AT.

@dataclass
class ProjectShape:
    exploring:       bool   # still figuring out what to build?
    complex_logic:   bool   # deep branching / loops / custom algorithms?
    non_specialists: bool   # will non-coders build or edit it?
    production:      bool   # will real users depend on it?


def recommend_setup(p: ProjectShape) -> dict:
    # ---- build tool -------------------------------------------------------
    if p.complex_logic and not p.non_specialists:
        build = "Write it in code (LangGraph)"
        why   = "Deep branching/loops make a visual canvas unreadable and untestable."
    elif p.exploring or p.non_specialists:
        build = "Langflow"
        why   = "Fastest path to a working pipeline; accessible to non-coders."
    else:
        build = "Langflow to prototype, then port the stable path to code"
        why   = "Speed early; testability and control once the design settles."

    # ---- observability ----------------------------------------------------
    if p.production:
        observability = "LangSmith - REQUIRED (baseline, not a milestone)"
        practices = [
            "trace everything, separate project per environment",
            "dataset built from real production failures",
            "experiments gate every change (read the per-example diff)",
            "online evaluators + alerts with a NAMED owner",
        ]
    else:
        observability = "LangSmith - strongly recommended from day one"
        practices = [
            "tracing costs nothing and saves hours on the first weird bug",
            "start a small dataset the moment you hit your first failure",
            "build the trace-reading habit BEFORE you need it in production",
        ]

    return {"build": build, "why": why,
            "observability": observability, "practices": practices}


if __name__ == "__main__":
    # a production assistant maintained partly by non-coders:
    print(recommend_setup(ProjectShape(
        exploring=False, complex_logic=False,
        non_specialists=True, production=True,
    )))
