M1 What Is Human-in-the-Loop? Concept Start here
Human-in-the-loop (HITL) means pausing an agent mid-run so a person can approve, edit, or reject what it's about to do before it happens. In LangGraph this is a first-class capability, not a bolt-on: the graph genuinely stops, persists its state, and waits.
Why this matters — use case
Your refund agent can read policy and decide a payout. The moment it can actually MOVE money, an autonomous mistake becomes an irreversible one. HITL puts a person on exactly those high-blast-radius steps - refunds over a threshold, account changes, anything regulated - while leaving the safe steps fully automated.
What's in this section
  • HITL turns an irreversible action into a reviewable proposal a human signs off on
  • LangGraph pauses the actual graph run and persists state - it isn't faking a pause with a prompt
  • The point is selective oversight: gate the risky steps, automate the rest
  • Four mechanics make it work: a checkpointer, a thread_id, interrupt(), and Command(resume=)
  • Over-gating is its own failure - humans who approve everything stop reading

Deep dive
The reason HITL matters more now than a year ago is that agents have graduated from producing text to taking actions - calling GitHub APIs, writing to databases, issuing refunds, sending email. When the only output was a suggestion, a wrong answer was cheap; a human read it and moved on. Once an agent holds a tool that moves money or mutates production data, every autonomous step carries the blast radius of that tool, and 'the LLM was confident' is not a control. HITL reintroduces a human at precisely the points where reversibility runs out. What makes LangGraph's version substantive rather than cosmetic is that it pauses the real execution: when a node calls interrupt(), the graph serializes its entire state to a checkpoint and returns control to your application, which can wait seconds or days before resuming from exactly that point. This is categorically different from a chatbot that simply asks 'are you sure?' and hopes the next message is an answer - there, the program never actually stopped and nothing was persisted, so a crash or a slow human loses everything. The design tension worth internalizing from the start is that oversight is a cost - human time, latency, coordination - so the goal is never to gate everything but to gate the actions that genuinely warrant it and let the rest run free.
python m1_what_is_hitl.py
# Human-in-the-loop = pause the agent BEFORE an irreversible action,
# let a person approve/edit/reject, then resume. In LangGraph the graph
# genuinely stops and persists - it is not a chatbot asking "are you sure?".

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command
from typing import TypedDict


class RefundState(TypedDict):
    order_id: str
    amount: float
    decision: str


# ---------------------------------------------------------------------------
# The idea in one node: gate only when the action is high-stakes
# ---------------------------------------------------------------------------
AUTO_APPROVE_LIMIT = 50.0    # small refunds run without a human

def process_refund(state: RefundState) -> RefundState:
    amount = state["amount"]

    # cheap, reversible, low-risk -> no human needed
    if amount <= AUTO_APPROVE_LIMIT:
        return {"decision": f"auto-approved ${amount:.2f}"}

    # expensive / irreversible -> PAUSE and ask a human
    verdict = interrupt({
        "action": "issue_refund",
        "order_id": state["order_id"],
        "amount": amount,
        "question": f"Approve a ${amount:.2f} refund for {state['order_id']}?",
    })
    # execution stops here until the app resumes with Command(resume=...)
    return {"decision": f"human {verdict} ${amount:.2f}"}


# ---------------------------------------------------------------------------
# A checkpointer is REQUIRED - it's what makes the pause durable
# ---------------------------------------------------------------------------
builder = StateGraph(RefundState)
builder.add_node("process_refund", process_refund)
builder.add_edge(START, "process_refund")
builder.add_edge("process_refund", END)

graph = builder.compile(checkpointer=InMemorySaver())   # no checkpointer -> no HITL

# ---------------------------------------------------------------------------
# Run it: a big refund pauses; a human decision resumes it
# ---------------------------------------------------------------------------
config = {"configurable": {"thread_id": "order-8891"}}

result = graph.invoke({"order_id": "ORD-8891", "amount": 500.0, "decision": ""}, config)
# result now contains an __interrupt__ - the graph is PAUSED, waiting.

# ...later, after a human clicks Approve in your UI...
final = graph.invoke(Command(resume="approved"), config)
print(final["decision"])        # -> "human approved $500.00"

# When to reach for HITL:
GATE_WHEN = ["irreversible", "high blast radius", "regulated", "low model confidence"]
SKIP_WHEN = ["reversible", "cheap to undo", "high volume + low stakes"]
⚑ Real-world scenario
A team shipped an autonomous refund agent that worked flawlessly in testing. In its second week it misread an edge-case policy and issued a large duplicate refund to a customer who had already been refunded manually - money that took weeks and a finance ticket to claw back. Nothing was 'broken': the model made a plausible call on an ambiguous input, which is exactly what models do. The fix was not a better prompt but a gate: any refund above a dollar threshold now pauses via interrupt() and routes to a human queue, while small, unambiguous refunds still process automatically. Losses from bad refunds dropped to near zero, and because only the large ones gate, the human reviewer sees a handful of cases a day rather than hundreds - so they actually read them.

Q1How is LangGraph HITL different from a chatbot asking 'are you sure?'
Node calls interrupt()→State saved to checkpoint→Control returns to caller→Resume from exact point
💡 Real pause, real persistence
A chatbot 'are you sure?' never actually stops the program - it just emits text and hopes the next message is a yes, so a crash or a slow reply loses all context. LangGraph genuinely halts the graph run: the node calls interrupt(), the entire state is serialized to a checkpoint, and control returns to your application, which can resume seconds or days later from that exact point. The pause is durable and the state survives, which is what makes it safe for actions that must not be lost or half-completed.
Q2When should you NOT add a human gate?
Is it reversible?→Is it cheap to undo?→High volume, low stakes?→If yes -> automate
💡 Don't gate the reversible
When the action is reversible and cheap to undo. HITL costs human time, latency, and coordination, and gating everything backfires: a human asked to approve hundreds of low-stakes actions a day learns to rubber-stamp, which destroys the value of the review for the cases that matter. Reserve gates for irreversible, high-blast-radius, or regulated steps. A read-only lookup or a draft that isn't committed anywhere doesn't need a human - only the step that actually commits does.
Q3Why does HITL require a checkpointer?
Pause needs saved state→Checkpointer persists it→thread_id locates it→Resume reads it back
💡 No memory, no pause
Because pausing is meaningless without somewhere to store what you paused. The checkpointer writes the graph's exact state when interrupt() fires, so the run can be resumed later - even after a process restart - from precisely that point. Without a checkpointer there is nothing to persist, so interrupt() has no way to hold the run open and the mechanism simply cannot work. In development an in-memory saver is fine; in production you use a durable one like Postgres so pauses survive restarts and deploys.
⚠ Common pitfall
Gating too much. It feels safer to put a human in front of every action, but a reviewer facing a flood of low-stakes approvals stops reading and rubber-stamps - so the one dangerous action in a hundred sails through unexamined. Oversight only works when it's selective. Gate the irreversible and the regulated; automate everything cheap to undo.

M2 Checkpointers & thread_id Persistence Foundation
The checkpointer is the memory that makes a pause durable; the thread_id is the cursor that says WHICH paused run you're resuming. Get these two right and interrupts just work; get them wrong and you resume the wrong user's graph.
Why this matters — use case
In production every customer conversation is its own thread. When a reviewer approves a refund for order 8891, the resume has to land on 8891's paused graph and no one else's. The checkpointer stores each thread's state; the thread_id routes the approval back to the right one.
What's in this section
  • A checkpointer saves graph state at every step, keyed by thread_id
  • thread_id is your persistent cursor: reuse it to resume, use a new one to start fresh
  • InMemorySaver for dev; PostgresSaver (or similar durable store) for production
  • One thread_id per independent conversation - collisions cross users' state
  • State survives process restarts with a durable checkpointer, so pauses can last days

Deep dive
A checkpointer is LangGraph's persistence layer: after each super-step it writes the complete graph state - channel values, the next nodes to run, pending interrupts - as a checkpoint associated with a thread_id. That thread_id, passed in the config at invoke time, is the single most important operational detail in HITL, because it is effectively a cursor into stored state. Pass a thread_id that already has history and the graph resumes from its last checkpoint; pass a fresh one and you get a brand-new run with empty state. This has a sharp consequence: thread_ids must be unique per independent unit of work - per user session, per task instance - because if two users share a thread_id, one user's resume can continue the other user's paused graph, leaking state and applying one person's approval to another's action. The choice of checkpointer implementation is a dev-versus-production distinction. InMemorySaver keeps everything in process memory, which is perfect for tests and notebooks but evaporates on restart - fatal for HITL, where a pause might outlive a deploy. A durable backend like PostgresSaver writes checkpoints to a database, so a graph paused for a human's approval survives restarts, rolling deploys, and multi-hour delays. The mental model that keeps this straight: the checkpointer is the filing cabinet, and the thread_id is the label on the folder you're asking for.

A support tool worked perfectly in staging and then, in production, occasionally applied one customer's refund approval to a different customer's order. The bug was a thread_id built from a non-unique value - a reused session key - so two concurrent conversations collided on the same checkpoint. When reviewer A approved order X and reviewer B approved order Y at nearly the same time, the resumes crossed. Q1What exactly does the thread_id control?
Pass existing id -> resume→Pass new id -> fresh start→Same id -> same checkpoint→It routes the resume
💡 Cursor into saved state
The thread_id is a cursor into checkpointed state. Passing a thread_id that already has history resumes that run from its last checkpoint; passing a new one starts a fresh run with empty state. In HITL it's what routes a human's resume back to the exact paused graph they're approving. That's why uniqueness matters so much - the thread_id, and nothing else, decides which run your Command(resume=) continues.
Q2What happens if two users share a thread_id?
Both write same checkpoint→Resumes get confused→A's approval hits B→State leaks across users
💡 Collision crosses state
Their state collides on the same checkpoint, and a resume meant for one can continue the other's paused graph - so user A's approval can execute against user B's action. This is a real production bug, not a theoretical one. Q3Why not just use InMemorySaver everywhere?
In-memory is process-local→Restart wipes it→Pauses can last days→Prod needs durability

Because a HITL pause can outlive your process. InMemorySaver keeps checkpoints in process memory, so a restart, crash, or deploy erases every paused run - and humans don't always respond in seconds; they might approve tomorrow. M3 interrupt() & Command(resume=) Core API Critical
interrupt() pauses a node and surfaces a value to your app; Command(resume=value) sends a value back, and that value becomes interrupt()'s return. The subtle, essential part: on resume the node re-executes from the top.
Why this matters — use case
This is the exact call your refund gate, your tool-review wrapper, and your input validator all make. Understanding the re-execution behaviour is what stops you from accidentally charging a card twice or sending an email twice when the node reruns on resume.
What's in this section
  • interrupt(payload) pauses the node and returns payload to the caller under the __interrupt__ key
  • Command(resume=value) resumes; value becomes the return of that interrupt() call
  • On resume the node RE-RUNS from the top - everything before interrupt() executes twice
  • So code above interrupt() must be side-effect free (no charges, no sends, no writes)
  • Multiple interrupts in one node resume in order, one Command(resume=) each

Deep dive
interrupt() and Command are a matched pair, and the mechanism connecting them has one behaviour that surprises almost everyone the first time. When a node calls interrupt(payload), LangGraph saves state, surfaces payload to the caller (available under the __interrupt__ key of the result), and suspends. You resume by invoking the graph with Command(resume=value); the graph re-enters the SAME node - and here is the crucial part - re-executes it from the beginning. All the code above the interrupt() line runs a second time. This time, when execution reaches interrupt(), instead of pausing it returns the value you passed in Command(resume=value), and the node continues past it. The reason it works this way is that LangGraph doesn't snapshot the Python call stack mid-function; it replays the node and substitutes the resumed value at the interrupt point. The practical rule that falls out of this is strict: any code before an interrupt() must be idempotent or side-effect free, because it runs on both the initial pass and the resume. Charging a card, sending an email, writing a row, or incrementing a counter above the interrupt() will happen twice. The fix is simple once you know it - do side-effecting work AFTER the interrupt(), or guard it so the second execution is a no-op - but the bug is nasty precisely because it only appears on resume, which happy-path testing often skips. When a node needs several human decisions, you place several interrupt() calls; on resume the node replays and each interrupt returns its corresponding resumed value in order.

# interrupt() pauses; Command(resume=v) sends v back as interrupt()'s return.
# THE catch: on resume the node RE-EXECUTES FROM THE TOP.

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command
from typing import TypedDict


class OrderState(TypedDict):
    order_id: str
    address: str
    charged: bool
    status: str


# ===========================================================================
# WRONG - side effect ABOVE interrupt() runs twice
# ===========================================================================
def place_order_BAD(state: OrderState) -> OrderState:
    charge_card(state["order_id"])                 # <-- runs on pass 1 AND on resume!
    ok = interrupt(f"Ship to {state['address']}?") # pause; on resume, re-enter from top
    return {"status": f"shipped ({ok})", "charged": True}
    # net effect in production: the customer is charged TWICE.


# ===========================================================================
# RIGHT - side effect BELOW interrupt(), so it happens once
# ===========================================================================
def place_order_GOOD(state: OrderState) -> OrderState:
    # everything above interrupt() must be safe to run twice (read-only):
    summary = f"Order {state['order_id']} -> {state['address']}"

    approved = interrupt({"confirm": summary})     # pause here

    # ...code below runs only after resume, exactly once:
    if approved == "yes":
        charge_card(state["order_id"])             # safe: single execution
        return {"charged": True, "status": "shipped"}
    return {"charged": False, "status": "cancelled"}


def charge_card(order_id: str) -> None:
    print(f"charging card for {order_id}")         # a REAL side effect


# ===========================================================================
# Lifecycle: invoke -> pause -> inspect -> resume
# ===========================================================================
builder = StateGraph(OrderState)
builder.add_node("place_order", place_order_GOOD)
builder.add_edge(START, "place_order")
builder.add_edge("place_order", END)
graph = builder.compile(checkpointer=InMemorySaver())

cfg = {"configurable": {"thread_id": "ORD-5501"}}

# 1. first invoke -> runs to interrupt(), then PAUSES
out = graph.invoke(
    {"order_id": "ORD-5501", "address": "12 Main St", "charged": False, "status": ""},
    cfg,
)
print(out["__interrupt__"])          # the payload we surfaced to the human

# 2. resume with the human's answer -> node RE-RUNS, interrupt() returns "yes"
final = graph.invoke(Command(resume="yes"), cfg)
print(final["status"])               # -> "shipped"   (charged exactly once)

# ---------------------------------------------------------------------------
# The rule, distilled
# ---------------------------------------------------------------------------
RESUME_RULES = [
    "everything ABOVE interrupt() runs on every resume -> keep it side-effect free",
    "do charges / sends / writes AFTER interrupt(), or make them idempotent",
    "always test the full pause->resume cycle, not just the pause",
    "N interrupts in a node -> N resumes, returned in order on replay",
]
⚑ Real-world scenario
A node called a payment API, then called interrupt() to have a human confirm a shipping address, then finished. In testing, everything looked fine - because the tests only ran the pause, never the resume. In production, every confirmed order charged the customer twice: the resume re-ran the node from the top, and the payment call sat ABOVE the interrupt(), so it fired again before execution reached the resumed confirmation. The team found it only when refunds started piling up. The fix was to move the charge below the interrupt() - so it runs once, after the human confirms - and to make the charge idempotent with an idempotency key as defense in depth. The lesson stuck: any node with an interrupt() gets tested through a full pause-and-resume cycle, never just the pause.

Q1What does the value in Command(resume=value) become?
Node hits interrupt()→App resumes with value→Node re-runs from top→interrupt() returns value
💡 Resume value = interrupt's return
It becomes the return value of the interrupt() call that paused the node. On the first pass interrupt(payload) suspends and hands payload to your app; when you resume with Command(resume=value), the node replays from the top and this time interrupt() doesn't pause - it returns value, and the node continues past it. So whatever the human decided (an 'approved' string, an edited object, a corrected number) is exactly what your node code receives from interrupt().
Q2Why is putting a side effect above interrupt() dangerous?
Resume replays the node→Top-of-node code re-runs→Side effect fires again→Double charge/send
💡 Above the line runs twice
Because resuming re-executes the node from the beginning, so any code above the interrupt() line runs a second time. If that code charges a card, sends an email, or writes a row, it happens twice - once on the initial pause, once on resume. The classic symptom is customers charged twice after confirming an order. Keep everything above interrupt() read-only, and do side-effecting work below it (or make it idempotent) so the replay can't double-fire.
Q3How do you handle a node that needs two human decisions?
Place interrupt() twice→First resume -> first value→Node replays→Second returns next value
💡 Two interrupts, two resumes
Place two interrupt() calls in the node. On the initial run it pauses at the first; you resume, the node replays and the first interrupt() returns your value, then execution reaches the second interrupt() and pauses again; a second Command(resume=) feeds the next value. Each interrupt consumes one resume, in order. Because the node replays each time, the same side-effect-free rule applies to all code above each interrupt point.
⚠ Common pitfall
Assuming the node continues from the interrupt() line on resume. It doesn't - it re-runs from the top, so every side effect above interrupt() fires again. This is the single most common HITL bug and it's invisible until you test resume, not just pause. Put side effects below the interrupt(), or guard them for idempotency.

M4 Dynamic vs Static Interrupts Placement Design
Two ways to place a pause: dynamic interrupt() called from inside node logic (conditional, anywhere), or static interrupt_before / interrupt_after set at compile time on a node boundary. Dynamic is usually the right default.
Why this matters — use case
You want to pause only when a refund exceeds a threshold - that's a runtime condition, so it belongs in dynamic interrupt(). You want to always pause before the 'execute_payment' node during a rollout - that's a fixed boundary, so a static breakpoint fits. Knowing which to reach for keeps the pause logic where it belongs.
What's in this section
  • Dynamic: call interrupt() inside a node - conditional, data-dependent, placed anywhere
  • Static: interrupt_before=['node'] / interrupt_after=['node'] at compile or invoke time
  • Dynamic keeps the pause next to the logic that decides it's needed - usually clearer
  • Static is handy for debugging, rollouts, or an always-on gate at a fixed boundary
  • Both need a checkpointer; both resume the same way

Deep dive
LangGraph offers two interrupt mechanisms and the distinction is about WHERE the decision to pause lives. A dynamic interrupt is the interrupt() function called from inside a node; it can be placed anywhere in your code and fired conditionally, so 'pause only if the amount exceeds the limit' or 'pause only if model confidence is low' is expressed naturally as an if-statement around the call. A static interrupt is a breakpoint declared at the graph level - interrupt_before or interrupt_after a named node, set at compile time or per-invocation - and it pauses unconditionally at that node boundary every time execution crosses it. The reason dynamic is the better default for real HITL is cohesion: the condition that decides a human is needed usually depends on the data flowing through the node, and interrupt() lets that condition live right beside the logic it guards, so a reader sees both together. Static breakpoints, by contrast, pause on a node whether or not this particular run warrants it, which is why they shine for a different job - debugging (pause before a node to inspect state), controlled rollouts (temporarily gate a newly-risky node for everyone while you build confidence), or a blanket policy gate at a fixed step. A useful way to hold the two apart: dynamic interrupts answer 'pause because of what's happening in this specific run', static breakpoints answer 'pause at this point in the graph, always'. They aren't mutually exclusive - a production graph often uses dynamic interrupts for its business gates and a static breakpoint or two during a rollout - and both rely on the same checkpointer and resume identically.

# Two placements for a pause. Choose by WHERE the decision to pause lives.

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command
from typing import TypedDict


class State(TypedDict):
    amount: float
    confidence: float
    result: str


# ===========================================================================
# DYNAMIC - interrupt() inside the node, fired CONDITIONALLY (the default)
# ===========================================================================
LIMIT = 100.0

def issue_refund(state: State) -> State:
    # the pause condition lives right next to the logic it guards
    high_value = state["amount"] > LIMIT
    low_conf   = state["confidence"] < 0.7

    if high_value or low_conf:
        decision = interrupt({
            "amount": state["amount"],
            "confidence": state["confidence"],
            "why": "over limit" if high_value else "low confidence",
        })
        if decision != "approved":
            return {"result": "refund blocked by reviewer"}

    return {"result": f"refunded ${state['amount']:.2f}"}


builder = StateGraph(State)
builder.add_node("issue_refund", issue_refund)
builder.add_edge(START, "issue_refund")
builder.add_edge("issue_refund", END)

# dynamic version needs nothing special at compile time:
graph_dynamic = builder.compile(checkpointer=InMemorySaver())


# ===========================================================================
# STATIC - breakpoint at a node boundary, ALWAYS pauses there
# ===========================================================================
# Good for debugging, rollouts, or a blanket gate at a fixed step.
graph_static = builder.compile(
    checkpointer=InMemorySaver(),
    interrupt_before=["issue_refund"],     # pause before this node, every run
    # interrupt_after=["issue_refund"],    # ...or after it
)
# You can also set breakpoints per-invocation for a one-off:
#   graph.invoke(inputs, config, interrupt_before=["issue_refund"])


# ===========================================================================
# Choosing between them
# ===========================================================================
def choose_placement(condition_depends_on_data: bool,
                     always_pause_here: bool,
                     debugging_or_rollout: bool) -> str:
    if condition_depends_on_data and not always_pause_here:
        return "DYNAMIC interrupt() - pause reflects THIS run's data"
    if debugging_or_rollout or always_pause_here:
        return "STATIC breakpoint - pause at this node boundary, always"
    return "DYNAMIC by default; reach for static only for fixed-boundary gates"

#   dynamic  -> "pause because of what's happening in this run"
#   static   -> "pause at this point in the graph, always"

Approve/reject is the pattern most people mean when they say HITL, and getting its shape right pays off everywhere because the other patterns are refinements of it. The structure is: the agent assembles a concrete proposal, interrupt() surfaces that proposal as a JSON-serializable payload, and the human's response - delivered as the resume value - is a decision the node then routes on. The first design point is the richness of the proposal payload. A human can only make a good call from what you show them, so the payload should carry everything needed to decide in one glance: the action, its parameters, the agent's reasoning, and any policy or risk context. # The workhorse: propose -> interrupt() -> route on the human's decision.
# approve / reject / edit are three branches off ONE gate.

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command
from typing import TypedDict, Literal


class RefundState(TypedDict):
    order_id: str
    amount: float
    policy_clause: str
    result: str


def propose_and_gate(state: RefundState) -> RefundState:
    # --- everything above interrupt() is READ-ONLY (it re-runs on resume) ---
    proposal = {
        "action": "issue_refund",
        "order_id": state["order_id"],
        "amount": state["amount"],
        "reasoning": state["policy_clause"],      # give the human WHY, not just WHAT
        "risk": "high" if state["amount"] > 500 else "normal",
    }

    # surface a RICH payload so the reviewer decides without leaving the screen
    decision = interrupt(proposal)
    # decision is whatever the UI sent via Command(resume=...)
    # e.g. {"verdict": "approve"} | {"verdict": "reject", "reason": "..."}
    #      | {"verdict": "edit", "amount": 450.0}

    verdict = decision.get("verdict")

    # --- side effects live BELOW interrupt(): they run exactly once ---
    if verdict == "approve":
        _execute_refund(state["order_id"], state["amount"])
        return {"result": f"approved & refunded ${state['amount']:.2f}"}

    if verdict == "edit":
        new_amount = decision["amount"]
        _execute_refund(state["order_id"], new_amount)
        return {"result": f"edited to ${new_amount:.2f} & refunded"}

    # reject is a REAL path - record it and inform the customer
    _record_refusal(state["order_id"], decision.get("reason", "not specified"))
    return {"result": "rejected: customer notified"}


def _execute_refund(order_id: str, amount: float) -> None:
    print(f"[refund] {order_id}: ${amount:.2f}")     # the real side effect

def _record_refusal(order_id: str, reason: str) -> None:
    print(f"[refusal] {order_id}: {reason}")


builder = StateGraph(RefundState)
builder.add_node("gate", propose_and_gate)
builder.add_edge(START, "gate")
builder.add_edge("gate", END)
graph = builder.compile(checkpointer=InMemorySaver())

# ---------------------------------------------------------------------------

Deep dive
Edit-state is the pattern for when the agent is close but not exactly right, which is common - an LLM extracts a mostly-correct set of fields, drafts a mostly-good message, computes a nearly-right amount. A yes/no gate is a blunt instrument here: reject throws away good work and forces a restart, while approve commits a known error. The edit pattern gives the human a third option - hand back a corrected value that the node writes into state and then continues from. Mechanically it's the same interrupt()/resume cycle, but the resume value is the new data rather than a verdict, and the node's job after interrupt() is to merge that data into state and proceed. The design consideration that separates a robust edit gate from a fragile one is validation of the human's input. It's tempting to trust an edited value because a human produced it, but humans transpose digits, paste the wrong field, and leave things blank; an edited amount of '4500' when they meant '450' is worse than the original error because it now carries human authority. So the edited value should pass the same validation the agent's output would - type, range, format - before it's written into state, and if it fails, the node can interrupt() again to ask for a correction (which is exactly the validate-input pattern, P4). The other subtlety is scope: edit only the fields you surface for editing. Letting a human overwrite arbitrary state invites accidental corruption of fields they didn't mean to touch, so a good edit gate returns a constrained shape and the node applies just those fields.

# Edit-state: the human returns a CORRECTED value; the node writes it and
# continues. Preserves good work instead of rejecting the whole attempt.

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command
from typing import TypedDict


class ClaimState(TypedDict):
    email: str
    amount: float
    order_id: str
    status: str


MAX_REASONABLE = 10_000.0

def _valid_amount(x) -> bool:
    return isinstance(x, (int, float)) and 0 < x <= MAX_REASONABLE


def review_extraction(state: ClaimState) -> ClaimState:
    # agent's extracted draft (read-only above interrupt())
    draft = {"amount": state["amount"], "order_id": state["order_id"]}

    # surface the draft for correction; human hands back an edited dict
    edited = interrupt({
        "message": "Correct any wrong fields, then submit.",
        "draft": draft,
        "editable": ["amount", "order_id"],       # constrain what can change
    })

    # --- validate the HUMAN's input; they mistype too ---
    new_amount = edited.get("amount", state["amount"])
    if not _valid_amount(new_amount):
        # bad edit -> ask again (this is the P4 validate-input pattern)
        edited = interrupt({
            "message": f"'{new_amount}' isn't a valid amount (0-{MAX_REASONABLE}). Re-enter.",
            "draft": draft,
            "editable": ["amount", "order_id"],
        })
        new_amount = edited.get("amount", state["amount"])

    # merge ONLY the editable fields, then proceed
    return {
        "amount": new_amount,
        "order_id": edited.get("order_id", state["order_id"]),
        "status": "corrected & submitted",
    }


builder = StateGraph(ClaimState)
builder.add_node("review", review_extraction)
builder.add_edge(START, "review")
builder.add_edge("review", END)
graph = builder.compile(checkpointer=InMemorySaver())

graph.invoke(
    {"email": "...refund my order...", "amount": 500.0,
     "order_id": "ORD-3310", "status": ""},
    cfg,
)

final = graph.invoke(Command(resume={"amount": 450.0}), cfg)
print(final["amount"], final["status"])        # -> 450.0 corrected & submitted

Deep dive
Tool-call review is the pattern that makes an autonomous agent safe to give real capabilities, and its key design move is granularity: you gate specific dangerous tools, not the agent's every step. An agent that pauses on every turn is useless - the human becomes the bottleneck and, worse, learns to rubber-stamp. # Wrap a DANGEROUS tool so its call pauses for review before executing.
# The agent reasons freely; the human only sees irreversible actions.

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command
from typing import TypedDict


class AgentState(TypedDict):
    tool: str
    args: dict
    outcome: str


# ---------------------------------------------------------------------------
# A reusable gate for risky tools. Read-only tools skip this entirely.
# ---------------------------------------------------------------------------
def review_tool_call(tool_name: str, args: dict) -> dict:
    """Pause for human review of a proposed tool call.
    Returns the args to execute with, or raises to deny."""
    review = interrupt({
        "review_type": "tool_call",
        "tool": tool_name,
        "proposed_args": args,
        "prompt": f"Agent wants to call {tool_name}({args}). Approve, edit, or deny?",
    })
    # review comes from Command(resume=...):
    #   {"action": "approve"}
    #   {"action": "edit", "args": {...}}
    #   {"action": "deny", "reason": "..."}
    action = review.get("action")
    if action == "approve":
        return args
    if action == "edit":
        return review["args"]                 # human-corrected arguments
    raise PermissionError(review.get("reason", "denied by reviewer"))


DANGEROUS = {"issue_refund", "close_account", "send_email"}   # gate these
# NOT gated: search_policy, get_order_status, ... (read-only, run freely)


def agent_acts(state: AgentState) -> AgentState:
    tool, args = state["tool"], state["args"]

    if tool in DANGEROUS:
        try:
            args = review_tool_call(tool, args)     # <-- pause happens here
        except PermissionError as e:
            # deny -> hand a refusal back to the agent's flow
            return {"outcome": f"blocked: {e}"}

    # side effect (the tool call) executes ONCE, below the interrupt()
    result = _run_tool(tool, args)
    return {"outcome": result}


def _run_tool(tool: str, args: dict) -> str:
    return f"{tool} executed with {args}"        # the real, irreversible call


builder = StateGraph(AgentState)
builder.add_node("act", agent_acts)
builder.add_edge(START, "act")
builder.add_edge("act", END)
graph = builder.compile(checkpointer=InMemorySaver())

cfg = {"configurable": {"thread_id": "sess-77"}}
graph.invoke({"tool": "issue_refund",
              "args": {"order_id": "ORD-1", "amount": 999.0},
              "outcome": ""}, cfg)
# reviewer spots a wrong amount and edits it before approving:
out = graph.invoke(Command(resume={"action": "edit",
                                   "args": {"order_id": "ORD-1", "amount": 99.0}}), cfg)
print(out["outcome"])            # -> issue_refund executed with {...amount: 99.0}

Two design points make it production-grade. Second, the loop needs an escape: a human who genuinely can't produce valid input (they don't know the reason code, the request is malformed) must not be trapped in an infinite prompt, so you cap retries or offer a cancel path that routes the graph somewhere sensible. MAX_RETRIES = 3

            "prompt": f"Enter a denial reason code for {state['order_id']}.",
            "allowed": sorted(ALLOWED_CODES),

    # escape hatch: don't trap the human in an infinite loop
    return {"reason_code": "NEEDS_TRIAGE", "status": "escalated for manual coding"}

Debugging: when a run goes wrong, you can rewind to the state just before the bad step and inspect exactly what the graph saw, rather than trying to reproduce it from scratch.     amount: float
    decision: str
    notice: str


def approve(state: State) -> State:
    verdict = interrupt({"amount": state["amount"], "q": "approve?"})

    return {"notice": f"Refund {state['decision']} for ${state['amount']:.2f}"}

# Oops - should have been a partial refund. REWIND and FORK a corrected branch.
# ---------------------------------------------------------------------------
# 1. list the history (newest first) and find the checkpoint BEFORE approve ran
history = list(graph.get_state_history(cfg))
for snap in history:

target = next(s for s in history if s.next == ("approve",))

fork_cfg = graph.update_state(
    target.config,
    {"amount": 250.0},                    # the correction
)
corrected = graph.invoke(Command(resume="approved"), fork_cfg)
print(corrected["notice"])                # -> Refund approved for $250.00

# Risk-scored gating: a computed score, not a flat threshold, decides the gate.
# low -> auto | medium -> log & run | high -> interrupt(). Scales HITL sanely.

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command
from typing import TypedDict


class RefundState(TypedDict):
    order_id: str
    amount: float
    customer_refunds_90d: int
    policy_confidence: float
    anomaly: bool
    result: str


HARD_GATE_FLOOR = 5_000.0     # always gate above this, whatever the score
LOW, HIGH = 0.3, 0.7          # band edges


def risk_score(s: RefundState) -> float:
    """Blend several signals into one 0-1 risk score."""
    score = 0.0
    score += min(s["amount"] / 2_000.0, 0.4)          # amount, capped
    score += 0.2 if s["customer_refunds_90d"] > 3 else 0.0   # frequent refunder
    score += (1.0 - s["policy_confidence"]) * 0.3     # weak policy match = riskier
    score += 0.3 if s["anomaly"] else 0.0             # anomaly signal
    return min(score, 1.0)


def gated_refund(state: RefundState) -> RefundState:
    score = risk_score(state)                          # pure - safe on replay

    # hard floor for catastrophic amounts, regardless of score
    force_gate = state["amount"] >= HARD_GATE_FLOOR

    if score < LOW and not force_gate:
        return {"result": f"auto-approved (risk {score:.2f})"}

    if score < HIGH and not force_gate:
        _audit_log(state["order_id"], score, band="medium")
        return {"result": f"ran + logged (risk {score:.2f})"}

    # high band (or forced) -> human gate
    verdict = interrupt({
        "order_id": state["order_id"],
        "amount": state["amount"],
        "risk_score": round(score, 2),
        "signals": {
            "frequent_refunder": state["customer_refunds_90d"] > 3,
            "policy_confidence": state["policy_confidence"],
            "anomaly": state["anomaly"],
        },
        "question": "High-risk refund - approve?",
    })
    _audit_log(state["order_id"], score, band="high", verdict=verdict)
    return {"result": f"human {verdict} (risk {score:.2f})"}


def _audit_log(order_id, score, band, verdict=None):
    print(f"[audit] {order_id} score={score:.2f} band={band} verdict={verdict}")


builder = StateGraph(RefundState)
builder.add_node("refund", gated_refund)
builder.add_edge(START, "refund")
builder.add_edge("refund", END)
graph = builder.compile(checkpointer=InMemorySaver())

out = graph.invoke({"order_id": "ORD-9001", "amount": 1800.0,

# high score -> paused; a reviewer approves:
final = graph.invoke(Command(resume="approved"), cfg)
print(final["result"])

A score that blends amount, customer history, policy-match confidence, and anomaly flags distinguishes genuine risk far better, so you can auto-approve the clearly-fine cases, log the middle, and send only the truly risky ones to a human - which is what makes HITL scale without burying reviewers.
Q2What is the middle 'log and run' band for?
Score is a model, can err→Medium = not clearly safe→Run but record it→Audit after the fact
💡 Safety net without blocking
It's a safety net for actions that aren't clearly safe but don't warrant blocking. A risk score is a model of risk, not risk itself, so the middle band lets borderline actions proceed while logging them for review after the fact - catching mis-scored cases without adding latency or reviewer load. It also produces the labeled data you need to tell whether your bands are calibrated and to improve the scoring function over time.
Q3Why keep a hard gate floor on top of the score?
Scores can be wrong→Some amounts are catastrophic→Always gate above a floor→Score-independent backstop
💡 Backstop the catastrophic
Because a scoring function can misjudge, and for genuinely catastrophic action types you don't want a model error to auto-approve. A hard floor - always gate any refund above a large absolute amount, regardless of score - is a score-independent backstop for the cases where the downside is severe enough that you never want them slipping through automatically. It costs almost nothing and bounds the worst-case failure of the scoring approach.
⚠ Common pitfall
Trusting the risk score as if it were risk itself and auto-approving everything below the high band. Scores misjudge; without a hard floor for catastrophic amounts and a logged middle band as a net, a single scoring error can wave through the exact action you most needed to catch. Keep the backstops.

Everything in this lab so far is the graph; production HITL is the graph plus the operational system that surrounds it, and that surrounding system is where real deployments succeed or fail. Start with persistence: development's in-memory saver is disqualifying here because a HITL pause can outlive a process, so you use a durable checkpointer (Postgres or equivalent) and treat the pause as state that must survive restarts, deploys, and multi-day human delays. Then the human interface: a paused thread is invisible unless something surfaces it, so you need an approval queue that lists pending interrupts and a UI that renders each interrupt() payload and captures the reviewer's decision to feed back as Command(resume=). Without this, 'the graph is paused' just means 'the work is stuck'. Next, the never-resumes case, which happy-path designs ignore: not every human responds, so you need a TTL or expiry job that scans for threads paused longer than some threshold and either auto-rejects them, escalates, or re-notifies - otherwise abandoned threads accumulate forever and customers wait indefinitely. Then identity and audit: in a regulated context you must be able to show who approved what and why, so every interrupt, resume, decision, risk score, and reviewer identity gets logged to an immutable trail. Two cross-cutting concerns tie back to earlier sections: thread_id uniqueness and pre-resume verification (M2) prevent one user's approval landing on another's action, and the re-execution rule (M3) means every side-effecting step in the production graph must be idempotent because resumes and time-travel forks replay nodes. Put together, a production HITL graph interleaves automated steps, dynamic risk-scored gates that pause only the consequential actions, durable persistence underneath, and an ops layer - queue, UI, expiry, audit - around it. The graph is maybe half the work; the operational envelope is the other half, and it's the half that determines whether the system is trustworthy.

from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt, Command
from typing import TypedDict
from datetime import datetime, timezone, timedelta


class RefundState(TypedDict):
    order_id: str
    amount: float
    risk: float
    result: str
    reviewer: str


# ---------------------------------------------------------------------------
# 1. The graph: automated steps + a risk-scored gate (A3) on the risky ones
# ---------------------------------------------------------------------------
def decide_refund(state: RefundState) -> RefundState:
    if state["risk"] < 0.7:
        return {"result": "auto-approved"}
    review = interrupt({
        "order_id": state["order_id"],
        "amount": state["amount"],
        "risk": state["risk"],
        "question": "Approve high-risk refund?",
    })
    # audit is a side effect -> below interrupt(), runs once
    _audit(state["order_id"], review, state["risk"])
    return {"result": f"human {review['verdict']}", "reviewer": review["reviewer"]}


# ---------------------------------------------------------------------------
# 2. Durable persistence - pauses survive restarts and multi-day delays
# ---------------------------------------------------------------------------
def build_graph(checkpointer):
    b = StateGraph(RefundState)
    b.add_node("decide", decide_refund)
    b.add_edge(START, "decide")
    b.add_edge("decide", END)
    return b.compile(checkpointer=checkpointer)

# ---------------------------------------------------------------------------
# 3. Approval queue - surface paused threads so reviewers can act
# ---------------------------------------------------------------------------
def list_pending(graph, thread_ids: list[str]) -> list[dict]:
    pending = []
    for tid in thread_ids:
        cfg = {"configurable": {"thread_id": tid}}
        snap = graph.get_state(cfg)
        if snap.tasks and snap.tasks[0].interrupts:
            pending.append({
                "thread_id": tid,
                "payload": snap.tasks[0].interrupts[0].value,
                "waiting_since": snap.created_at,
            })
    return pending

def approve(graph, thread_id: str, verdict: str, reviewer: str) -> dict:
    cfg = {"configurable": {"thread_id": thread_id}}
    # verify the thread is really what we think before resuming (M2)
    snap = graph.get_state(cfg)
    assert snap.tasks and snap.tasks[0].interrupts, "thread not awaiting review"
    return graph.invoke(Command(resume={"verdict": verdict, "reviewer": reviewer}), cfg)


# ---------------------------------------------------------------------------
# 4. TTL / expiry - handle threads a human never comes back to
# ---------------------------------------------------------------------------
def expire_stale(graph, thread_ids: list[str], ttl_hours: int = 24) -> None:
    cutoff = datetime.now(timezone.utc) - timedelta(hours=ttl_hours)
    for item in list_pending(graph, thread_ids):
        if item["waiting_since"] < cutoff:
            # re-notify, escalate, or auto-reject - policy choice:
            approve(graph, item["thread_id"], verdict="auto-rejected", reviewer="system:ttl")


# ---------------------------------------------------------------------------
# 5. Audit trail - who approved what, when, at what risk (regulated contexts)
# ---------------------------------------------------------------------------
def _audit(order_id: str, review: dict, risk: float) -> None:
    record = {
        "ts": datetime.now(timezone.utc).isoformat(),
        "order_id": order_id,
        "verdict": review.get("verdict"),
        "reviewer": review.get("reviewer"),
        "risk": risk,
    }
    print("[AUDIT]", record)      # in prod: write to an immutable store

⚑ Real-world scenario
A team took their well-tested refund graph to production and hit every gap the patterns don't cover. Paused threads vanished on the first deploy - they were still on the in-memory saver, so they moved to Postgres. Reviewers had no way to see what was waiting - so they built a queue view that listed pending interrupts and rendered each payload with an approve/edit/deny control wired to Command(resume=). Then threads began piling up unresolved because some customers' cases were assigned to a reviewer who'd gone on leave - so they added a TTL job that re-notified after a day and escalated after three. Finally, a compliance review asked who had approved a particular large refund and they couldn't fully answer - so they added an audit trail capturing reviewer identity, timestamp, the risk score, and the decision for every gated action. Q1Why is a durable checkpointer non-negotiable in production?
HITL pause can last days→Restarts/deploys happen→In-memory state dies→Postgres survives
💡 Pauses outlive processes
Because a HITL pause can outlive the process that created it - a human might approve tomorrow, and a deploy or restart will happen in between. InMemorySaver keeps state in process memory, so any restart erases every paused run, stranding real customer actions. A durable checkpointer like PostgresSaver writes checkpoints to a database, so pauses survive restarts, deploys, and multi-day delays. It's the difference between a pause that holds and one that silently disappears.
Q2What has to happen for threads a human never resumes?
Not everyone responds→Scan for stale pauses→Re-notify or escalate→Or auto-resolve on TTL
💡 Design for never-resumes
You need a TTL or expiry job, because not every human responds - reviewers go on leave, cases fall through cracks. Without it, abandoned threads accumulate forever and customers wait indefinitely. The job scans for threads paused longer than a threshold and applies a policy: re-notify, escalate to another reviewer, or auto-resolve (reject/approve) with a system identity recorded. Designing for the never-resumes case is a hallmark of production HITL that happy-path prototypes skip.
Q3What makes a production HITL graph auditable?
Capture reviewer identity→Log decision + timestamp→Record the risk score→Immutable trail
💡 Log who, what, when, why
An audit trail that logs, for every gated action, the interrupt payload, the reviewer's identity and decision, the timestamp, and the risk score that triggered the gate - written to an immutable store. In regulated contexts you must be able to show after the fact who approved what and why, and reconstruct the basis for each decision. Building this in from the start, rather than retrofitting it after a compliance review asks a question you can't answer, is what makes the system trustworthy.
⚠ Common pitfall
Treating the graph as the finished product and skipping the operational envelope. A perfectly correct graph with in-memory state, no approval queue, no expiry job, and no audit trail is not production-ready - pauses vanish on deploy, reviewers can't act, dead threads pile up, and you can't prove who approved what. The ops layer is half the system.
