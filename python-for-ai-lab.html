NP1NumPy Arrays & Vectorization Foundations Start here
The ndarray is the foundation of every AI stack — embeddings, weights, batches, and logits are all NumPy-style arrays. The single most important habit is vectorization: expressing computation as whole-array operations instead of Python loops, which is often 10–100× faster.
WHY THIS MATTERS
Every embedding you store, every batch you feed a model, and every similarity score you compute is an array operation. Writing these as Python for loops is the number-one performance mistake in AI code — the same work vectorized runs orders of magnitude faster because it drops into optimized C.
KEY POINTS
  • An ndarray has a dtype (e.g. float32) and a shape (a tuple of dimensions) — both matter enormously for memory and correctness.
  • Vectorized operations apply element-wise across the whole array at C speed; prefer them over Python loops.
  • Broadcasting lets arrays of different shapes combine without copying — the mechanic behind adding a bias vector to a batch.
  • float32 vs float64: models use float32 to halve memory and speed up compute; be deliberate about dtype.
INSTALL
pip install numpy
DEEP DIVE
A NumPy array is a contiguous block of memory plus metadata describing how to interpret it: the dtype (how many bytes per element and how to read them) and the shape (how the flat buffer maps to dimensions). That contiguity is why vectorized operations are fast — the CPU streams through memory predictably and NumPy dispatches to optimized C or BLAS routines, with no per-element Python overhead. When you write a * 2 + b, NumPy runs the whole thing in compiled code; when you write a Python loop doing the same, every iteration pays interpreter cost. The rule of thumb in AI code: if you find yourself writing a for loop over array elements, stop and ask whether a vectorized expression, a broadcast, or a NumPy reduction (sum, mean, argmax) does it instead. dtype discipline matters too — a model's weights in float32 take half the RAM of float64 and run faster on most hardware, but you must convert deliberately, because an accidental float64 embedding array doubles your memory footprint silently.
pythonvectorize.py
import numpy as np

# An embedding batch: 4 vectors of dimension 8, in float32 (model-native)
batch = np.random.rand(4, 8).astype(np.float32)
print(batch.shape, batch.dtype)   # (4, 8) float32

# SLOW - Python loop, element by element (never do this in AI code)
scaled_slow = np.empty_like(batch)
for i in range(batch.shape[0]):
    for j in range(batch.shape[1]):
        scaled_slow[i, j] = batch[i, j] * 2.0 + 1.0

# FAST - one vectorized expression, runs in C over the whole array
scaled_fast = batch * 2.0 + 1.0

# Broadcasting: add a per-dimension bias (shape (8,)) to every row (shape (4,8))
bias = np.arange(8, dtype=np.float32)
biased = batch + bias            # (4,8) + (8,) -> (4,8), no copy of bias

# Reductions replace accumulator loops
row_means = batch.mean(axis=1)   # mean of each vector -> shape (4,)
best_dim  = batch.argmax(axis=1) # index of largest value per row -> shape (4,)
print(row_means.shape, best_dim)
COMMON PITFALL
Mixing dtypes silently upcasts. Adding a float64 scalar or array to a float32 model tensor promotes the result to float64 — doubling memory and often breaking downstream code that expects float32. Check .dtype after operations, and convert explicitly with .astype(np.float32) when feeding models.
HOW IT CONNECTS
Vectorization and broadcasting are the mechanics behind everything in Pillar 1 and beyond: Pandas is built on NumPy, embeddings are float32 arrays, and the cosine-similarity code you'll write for retrieval is one broadcast plus one reduction. Master this and the rest is composition.
NP2Shapes, Axes & Reshaping Foundations
Ninety percent of NumPy bugs are shape bugs. Understanding axes, reshape, and how operations collapse or preserve dimensions is what lets you manipulate batches, sequences, and embedding matrices with confidence.
WHY THIS MATTERS
A model expects input shaped (batch, seq_len, hidden); your data arrives as (seq_len, hidden). Knowing how to add a batch axis, transpose, or reshape without corrupting the data is a daily task in any AI pipeline.
KEY POINTS
  • axis=0 runs down rows (across the batch); axis=1 runs across columns (within a vector). Reductions remove the axis they act on.
  • reshape reinterprets the same buffer with a new shape — no copy, so it's free — as long as the total element count matches.
  • -1 in a reshape means 'infer this dimension' — x.reshape(batch, -1) flattens everything after the batch axis.
  • None / np.newaxis inserts a size-1 axis; transpose / .T reorders axes for matmul alignment.
DEEP DIVE
Think of shape as the grammar of your data and axes as the direction of an operation. When you call arr.sum(axis=0) on a (4, 8) array, you collapse the 4 rows and get an (8,) result — one summed value per column. axis=1 collapses the 8 columns and gives (4,) — one value per row. The axis you name is the one that disappears. Reshaping is different: it keeps every element but re-describes how the flat buffer is chunked into dimensions, which is why it's essentially free (no data moves) as long as the element count is preserved. The -1 placeholder tells NumPy to solve for one dimension given the others — indispensable for flattening a batch of images or token embeddings before a dense layer. Adding axes with None is how you line shapes up for broadcasting: turning a (N,) vector into (N, 1) or (1, N) decides whether it broadcasts down rows or across columns. Transposing reorders axes so matrices align for multiplication — the classic fix when matmul complains about mismatched inner dimensions.
pythonshapes.py
import numpy as np

# A single sequence of token embeddings: (seq_len=5, hidden=8)
seq = np.random.rand(5, 8).astype(np.float32)

# Models want a batch axis: (batch=1, seq_len=5, hidden=8)
batched = seq[None, :, :]         # or np.expand_dims(seq, 0)
print(batched.shape)              # (1, 5, 8)

# Flatten everything after the batch axis -> (1, 40) for a dense layer
flat = batched.reshape(batched.shape[0], -1)
print(flat.shape)                 # (1, 40)

# Axis-aware reductions
scores = np.random.rand(4, 10)    # (batch=4, classes=10) logits
probs_sum = scores.sum(axis=1)    # sum over classes -> (4,)  axis 1 removed
top_class = scores.argmax(axis=1) # best class per row  -> (4,)

# Reshape for matmul alignment: (4,8) @ (8,3) -> (4,3)
W = np.random.rand(8, 3).astype(np.float32)
out = seq[:4] @ W                 # inner dims (8) match -> (4, 3)
print(out.shape)
COMMON PITFALL
A reshape that 'works' can still be wrong. reshape only checks the element count, not the meaning — reshaping (batch, seq, hidden) in the wrong order silently interleaves your data. Always reason about which axis maps where, and sanity-check a couple of values after any non-trivial reshape.
HOW IT CONNECTS
Shape fluency is what makes the Pandas ↔ NumPy handoff (df.values) and the embedding math in the LLM pillar feel effortless. Every 'dimension mismatch' error you'll ever hit is solved by the axis and reshape reasoning here.
NP3Cosine Similarity — Vectorized Retrieval Math Applied
Semantic search ranks stored vectors by cosine similarity to a query vector. Done right, scoring a whole corpus is a single normalized matrix multiply — the exact math inside every vector database.
WHY THIS MATTERS
This is the retrieval step of RAG. A user query becomes an embedding; you score it against thousands of chunk embeddings and take the top-k. Writing this vectorized (not as a loop over chunks) is what makes retrieval fast enough to serve.
KEY POINTS
  • Cosine similarity = dot product of L2-normalized vectors; it measures direction, ignoring magnitude.
  • Normalize once: divide each vector by its L2 norm, then similarity is just query @ corpus.T.
  • np.linalg.norm(x, axis=1, keepdims=True) keeps the axis so broadcasting divides row-wise cleanly.
  • argpartition beats a full sort for top-k when the corpus is large.
DEEP DIVE
Cosine similarity asks: do these two vectors point in the same direction? It's the dot product divided by the product of the two magnitudes, which is exactly the dot product of the unit-length versions of each vector. That reframing is the whole performance trick — if you normalize every vector to length 1 up front, similarity collapses to a plain dot product, and scoring a query against an entire corpus becomes one matrix multiply: query_unit @ corpus_unit.T. Normalization needs keepdims=True so the norms keep their column axis and broadcast cleanly when you divide. For top-k selection, a full sort is wasteful when you only want the best handful — np.argpartition does a partial ordering that puts the top-k in place in linear time, and you sort just those. This is not a toy: it is precisely what a vector store does under the hood, and understanding it means you can debug retrieval quality, reason about why magnitude-sensitive dot-product indexes behave differently, and implement a fallback search in a few lines when you need one.
pythoncosine.py
import numpy as np

def l2_normalize(x: np.ndarray) -> np.ndarray:
    """Scale each row to unit length so dot product == cosine similarity."""
    norms = np.linalg.norm(x, axis=1, keepdims=True)   # (N,1) keep axis
    return x / np.clip(norms, 1e-12, None)             # avoid divide-by-zero

# Corpus of 1000 chunk embeddings, query of the same dimension
corpus = np.random.rand(1000, 384).astype(np.float32)
query  = np.random.rand(384).astype(np.float32)

corpus_u = l2_normalize(corpus)
query_u  = query / np.clip(np.linalg.norm(query), 1e-12, None)

# Score the ENTIRE corpus in one matmul -> (1000,)
scores = corpus_u @ query_u

# Top-5 without fully sorting 1000 items
k = 5
top_idx = np.argpartition(-scores, k)[:k]          # unordered top-k
top_idx = top_idx[np.argsort(-scores[top_idx])]    # order just those 5
for rank, i in enumerate(top_idx, 1):
    print(f"{rank}. chunk {i:4d}  score={scores[i]:.4f}")
COMMON PITFALL
Forgetting to normalize gives you a raw dot product, which rewards long vectors regardless of direction — so frequent or verbose chunks dominate results for the wrong reason. If your retrieval quality is mysteriously biased toward certain chunks, check whether you normalized both sides.
HOW IT CONNECTS
This is the bridge from Pillar 1 into the LLM pillar: the embeddings you score here come from an embedding API, and the top-k chunks feed into a prompt. The same normalize-then-matmul pattern is what pgvector, FAISS, and every vector DB implement at scale.
NP4Broadcasting — The Rules in Depth Deep Dive
Broadcasting is how NumPy combines arrays of different shapes without copying. Knowing the exact rules — align from the right, size-1 dimensions stretch — lets you write batch operations, per-feature scaling, and pairwise distances cleanly instead of with loops.
WHY THIS MATTERS
Subtracting a mean vector from a batch, scaling each feature by its own factor, computing all pairwise distances between two sets of vectors — every one is a broadcast. Getting the shapes to line up deliberately (with None/reshape) is a core NumPy skill.
KEY POINTS
  • Shapes align from the rightmost dimension leftward; missing left dims are treated as size 1.
  • Two dimensions are compatible if they're equal or one of them is 1 (the 1 stretches).
  • Insert size-1 axes with None to control which way an array broadcasts.
  • Pairwise ops: A[:, None, :] - B[None, :, :] gives an (n, m, d) difference tensor.
DEEP DIVE
Broadcasting has exactly two rules, and internalizing them removes most NumPy shape confusion. First, NumPy aligns the shapes of two arrays starting from the rightmost dimension and working left; if one array has fewer dimensions, it's treated as having size-1 dimensions prepended. Second, at each aligned position the two sizes must either be equal, or one of them must be 1 — in which case that size-1 dimension is virtually stretched to match the other, without any data being copied. That's the entire mechanism, and it explains every broadcast you'll write. Adding a bias vector of shape (d,) to a batch of shape (n, d) works because the vector is treated as (1, d) and its row is stretched across all n rows. The power comes from controlling the alignment yourself by inserting size-1 axes with None: to compute all pairwise differences between an (n, d) set and an (m, d) set, you reshape to (n, 1, d) and (1, m, d), and broadcasting produces the full (n, m, d) tensor of differences — the foundation of pairwise distance and attention-style computations — with no explicit loop. When a broadcast fails, the error names the incompatible dimension, and the fix is almost always inserting or removing a size-1 axis so the shapes align the way you intend.
pythonbroadcasting.py
import numpy as np

batch = np.random.rand(4, 3).astype(np.float32)   # (n=4 samples, d=3 features)

# Per-feature standardization: subtract mean, divide by std (both shape (3,))
mean = batch.mean(axis=0)          # (3,)  -> treated as (1,3), stretches over rows
std  = batch.std(axis=0)           # (3,)
standardized = (batch - mean) / std

# Per-sample scaling: one factor per row -> need shape (4,1) to stretch over cols
weights = np.array([1.0, 2.0, 0.5, 1.5], dtype=np.float32)
scaled = batch * weights[:, None]  # (4,1) * (4,3) -> (4,3)

# All pairwise squared distances between A (n,d) and B (m,d)
A = np.random.rand(5, 3); B = np.random.rand(2, 3)
diff = A[:, None, :] - B[None, :, :]      # (5,1,3) - (1,2,3) -> (5,2,3)
dist2 = (diff ** 2).sum(axis=2)           # -> (5,2) pairwise squared distances
print(dist2.shape)
COMMON PITFALL
A (n,) vector broadcasts across columns, not rows — so subtracting per-sample values without reshaping to (n,1) silently does the wrong thing (or errors if sizes differ). When a broadcast 'works' but results look wrong, check whether you needed [:, None] to orient the stretch.
HOW IT CONNECTS
Broadcasting is the engine under NP3's cosine similarity, NP5's einsum, and every per-feature or per-sample transform in Pandas and model code. The pairwise-difference pattern here reappears directly in distance metrics and attention.
NP5einsum & Matrix Operations Deep Dive
einsum expresses almost any multiply-and-sum operation — dot products, matmuls, batch matmuls, attention scores — in one readable string. It's the clearest way to write and reason about the tensor contractions at the heart of ML.
WHY THIS MATTERS
Batched attention scores, weighted sums over embeddings, per-head projections — these are all contractions that are easy to get wrong with reshape+transpose+matmul gymnastics. einsum states the index pattern explicitly, so the operation reads like its math and mistakes are visible.
KEY POINTS
  • einsum notation labels each axis; repeated labels are summed, output labels are kept.
  • 'ij,jk->ik' is matmul; 'bij,bjk->bik' is batched matmul; 'i,i->' is a dot product.
  • It makes the contraction explicit and readable — no guessing what a chain of transposes does.
  • Great for attention: 'bqd,bkd->bqk' scores every query against every key per batch.
DEEP DIVE
einsum (Einstein summation) is a small notation that expresses the vast family of multiply-then-sum operations with total clarity. You write a string naming the axes of each input and the axes of the output: any index that appears in the inputs but not the output is summed over, and any index kept in the output is preserved. That single rule covers an enormous range. 'ij,jk->ik' names a matrix multiply — the shared j is summed, leaving i and k. 'i,i->' is a dot product — both vectors share index i, which is summed to a scalar with no output indices. Prefix a batch dimension and 'bij,bjk->bik' becomes a batched matmul that keeps b separate. The reason this matters for ML is that the core operations — projecting embeddings, computing attention scores, applying per-head transforms — are all contractions, and expressing them with reshape, transpose, and matmul is error-prone and opaque: a chain of .transpose(0,2,1) calls hides what's actually being contracted. With einsum the index pattern is the operation, so attention scores read as 'bqd,bkd->bqk' — for each batch, contract the shared feature dimension d to score every query q against every key k — and the shape of the result is right there in the output labels. It's both a writing tool and a reasoning tool.
pythoneinsum.py
import numpy as np

# Dot product: sum over the shared index i
a = np.arange(4.0); b = np.arange(4.0)
print(np.einsum("i,i->", a, b))          # scalar

# Matrix multiply: contract shared j
X = np.random.rand(4, 8); W = np.random.rand(8, 3)
print(np.einsum("ij,jk->ik", X, W).shape)      # (4, 3)

# Batched matmul: keep batch b, contract j
Xb = np.random.rand(16, 4, 8); Wb = np.random.rand(16, 8, 3)
print(np.einsum("bij,bjk->bik", Xb, Wb).shape) # (16, 4, 3)

# Attention scores: per batch, score each query against each key
# queries (b, q, d), keys (b, k, d) -> scores (b, q, k), contracting feature dim d
Q = np.random.rand(2, 5, 8); K = np.random.rand(2, 7, 8)
scores = np.einsum("bqd,bkd->bqk", Q, K)       # (2, 5, 7)
print(scores.shape)
COMMON PITFALL
einsum's flexibility makes it easy to write a contraction that runs but sums the wrong axis — the output shape may even look plausible. Always sanity-check the output shape against what the math should produce, and name the axes meaningfully (b, q, k, d) so the string reads as the intended operation.
HOW IT CONNECTS
einsum is broadcasting's precise cousin: where NP4 stretches shapes, einsum contracts them. Together they cover essentially all the tensor math in ML, and the attention-score pattern here is the literal core of transformer models.
NP6Memory, Views vs Copies & dtypes Performance
At AI-data scale, memory is a real constraint. Knowing when NumPy returns a view (shares memory) versus a copy, and choosing dtypes deliberately, is what keeps large embedding matrices and datasets from silently blowing up your RAM.
WHY THIS MATTERS
A million 768-dim float32 embeddings is ~3 GB; in float64 it's ~6 GB. Slicing that array can share or copy memory depending on how you do it. Understanding views vs copies prevents both accidental 2× memory blowups and subtle bugs where a 'copy' mutates the original.
KEY POINTS
  • Basic slicing returns a view (shares memory) — mutating it changes the original.
  • Fancy indexing (with a list/array of indices or a boolean mask) returns a copy.
  • dtype sets memory per element: float32 is half of float64; choose it deliberately for big arrays.
  • .copy() forces an independent array; np.shares_memory(a, b) checks the relationship.
DEEP DIVE
NumPy's speed and memory behavior both come from the same source — arrays are contiguous buffers — and understanding when operations share versus duplicate that buffer prevents two opposite failure modes: silent memory blowups and silent mutation bugs. Basic slicing (with ranges and integers) returns a view: a new array object that points into the same underlying memory, so it's free to create and mutating it changes the parent. That's efficient but surprising if you expected an independent copy — modifying a slice you thought was safe corrupts the original. Fancy indexing — selecting with a list or array of indices, or a boolean mask — cannot generally be expressed as a view into contiguous memory, so it returns a copy, which is safe to mutate but costs memory and time proportional to its size. Knowing which is which lets you avoid accidentally duplicating a multi-gigabyte embedding matrix, and lets you reach for .copy() deliberately when you truly need independence. dtype is the other lever: it fixes how many bytes each element occupies, so a large array in float64 uses exactly twice the RAM of the same array in float32. Models use float32 precisely for this reason, and being deliberate about dtype — converting once, checking after operations that might upcast — is what keeps large datasets and embedding stores inside your memory budget. np.shares_memory is the tool for settling any doubt about whether two arrays alias.
pythonmemory.py
import numpy as np

emb = np.random.rand(1_000_000, 768).astype(np.float32)
print(f"{emb.nbytes / 1e9:.2f} GB")          # ~3.07 GB (float64 would be ~6.14)

# Basic slice -> VIEW: shares memory, mutation propagates
first10 = emb[:10]
print(np.shares_memory(emb, first10))        # True
first10[0, 0] = -1.0
print(emb[0, 0])                             # -1.0  (parent changed!)

# Fancy / mask indexing -> COPY: independent memory
subset = emb[[0, 5, 9]]                       # list index -> copy
print(np.shares_memory(emb, subset))         # False

# Force independence when you need it
safe = emb[:10].copy()
safe[0, 0] = 99.0                             # does NOT touch emb

# Deliberate dtype halves memory for big arrays
big64 = np.ones((100_000, 768))              # float64 by default
big32 = big64.astype(np.float32)
print(big64.nbytes // big32.nbytes)          # 2
COMMON PITFALL
Assuming a slice is an independent copy leads to action-at-a-distance bugs: you modify what you think is a local subset and silently corrupt the original array. When you need to mutate a slice without affecting the parent, call .copy() explicitly — and when memory is tight, remember fancy indexing duplicates.
HOW IT CONNECTS
View/copy awareness matters the moment you handle real embedding stores (Pillar 5) or large datasets (Pillar 4), and dtype discipline ties back to NP1. This is the section that keeps 'it works on a sample' from becoming 'it OOMs on the full data'.
PD1Pandas DataFrames — Loading & Inspecting Data Foundations
Before data reaches a model it lives in a DataFrame: a labeled 2-D table built on NumPy. Loading, inspecting, and understanding dtypes is the first step of every dataset, evaluation set, and log analysis.
WHY THIS MATTERS
Your training examples, eval results, and production logs all arrive as CSVs or JSON. Pandas is how you load them, spot missing values, check class balance, and get the data clean enough to trust before you build anything on top of it.
KEY POINTS
  • A DataFrame is columns of typed Series (each a NumPy array) sharing an index.
  • read_csv / read_json load data; head, info, describe inspect it fast.
  • dtypes matter: an object column is often unparsed strings; numeric columns should be int/float.
  • isna().sum() and value_counts() are your first two sanity checks on any new dataset.
INSTALL
pip install pandas
DEEP DIVE
A DataFrame is best understood as an ordered dict of Series that all share one index, where each Series is a typed NumPy array under the hood. That heritage is why Pandas is fast for column operations and why dtype awareness carries straight over from NumPy. When you load a CSV, the first thing to do is not to start transforming — it's to look: info() tells you row count, column dtypes, and non-null counts in one view, which immediately surfaces the two most common data problems, wrong types and missing values. An object dtype on a column you expected to be numeric is a red flag that something didn't parse — a stray unit, a thousands separator, a sentinel like 'N/A'. describe() gives distribution shape for numeric columns so outliers and impossible values jump out. For an AI dataset specifically, two checks matter before anything else: isna().sum() to quantify missingness per column, and value_counts() on your label column to see class balance, because a wildly imbalanced or leaked label set will quietly ruin an evaluation no matter how good the model is.
pythonload_inspect.py
import pandas as pd

# Load a labeled dataset (e.g. refund requests with an outcome label)
df = pd.read_csv("refund_requests.csv")

# First look - never skip these
print(df.shape)              # (rows, columns)
df.info()                    # dtypes + non-null counts per column
print(df.head(3))            # eyeball the first rows

# Two AI-specific sanity checks
print(df.isna().sum())       # missing values per column
print(df["outcome"].value_counts(normalize=True))  # class balance

# Spot an object column that should be numeric
if df["amount"].dtype == object:
    df["amount"] = pd.to_numeric(df["amount"].str.replace("$", "", regex=False),
                                 errors="coerce")   # bad values -> NaN
print(df["amount"].describe())
COMMON PITFALL
errors="coerce" turns unparseable values into NaN silently — convenient, but if half your column becomes NaN you've hidden a real data problem. After any coercion, re-check isna().sum() to confirm you fixed the type without deleting the data.
HOW IT CONNECTS
Clean, well-typed DataFrames are the input to feature engineering (PD2) and the container for evaluation results throughout the labs. The dtype discipline from NumPy pays off directly here.
PD2Selecting, Filtering & Transforming Foundations
The core Pandas verbs — loc, boolean masks, assign, groupby — let you slice, filter, and reshape data without loops. This is how you build evaluation subsets, features, and aggregate metrics.
WHY THIS MATTERS
You need the failure cases where confidence was low, or mean latency per model version, or a new feature column derived from two others. Each is a one-liner with the right Pandas verb — and a slow, error-prone loop without it.
KEY POINTS
  • df.loc[mask, cols] selects by boolean condition and label — the primary, unambiguous accessor.
  • Boolean masks combine with &, |, ~ (parenthesize each condition).
  • assign adds derived columns functionally; groupby(...).agg(...) computes per-group metrics.
  • Vectorized string and datetime accessors (.str, .dt) replace row loops.
DEEP DIVE
Pandas rewards a vectorized, expression-oriented style just like NumPy. Selection is the foundation: loc takes a row selector and a column selector, and the row selector is usually a boolean mask — a Series of True/False the same length as the frame. Masks compose with bitwise operators, not Python's and/or, and each comparison must be parenthesized because of operator precedence. Once you can express 'the rows where confidence < 0.5 and model == v2' as a mask, you can filter, count, or assign against it uniformly. assign keeps transformations functional and chainable — it returns a new frame with the added column, which reads cleanly and avoids the mutation-order confusion of repeated bracket assignment. The real power tool is groupby: split rows into groups by one or more keys, apply an aggregation to each, and combine the results — this is how you turn a raw log of per-request rows into 'mean latency and error rate per model version' in a single expression. And the .str and .dt accessors vectorize text and time operations so you never loop to lowercase a column or extract an hour.
pythontransform.py
import pandas as pd

df = pd.read_csv("eval_runs.csv")   # cols: model, confidence, latency_ms, ok, ts

# Filter: low-confidence failures (parenthesize each condition!)
mask = (df["confidence"] < 0.5) & (~df["ok"])
failures = df.loc[mask, ["model", "confidence", "latency_ms"]]

# Derive columns functionally
df = df.assign(
    slow = df["latency_ms"] > 1000,
    hour = pd.to_datetime(df["ts"]).dt.hour,
)

# Per-model metrics in one groupby
report = (df.groupby("model")
            .agg(n=("ok", "size"),
                 accuracy=("ok", "mean"),
                 p95_latency=("latency_ms", lambda s: s.quantile(0.95)))
            .sort_values("accuracy", ascending=False))
print(report)
COMMON PITFALL

PD3Vectorized Pandas & Avoiding Loops Performance
The difference between Pandas code that scales and code that crawls is whether you loop. apply row-wise and iterrows are slow; vectorized column operations and the right merge/pivot are fast.
WHY THIS MATTERS
Processing a million log rows, joining predictions to ground truth, or building a features table — do it vectorized and it's seconds; do it with iterrows and it's minutes to hours. At AI-data scale, this is the difference between usable and not.
KEY POINTS
  • iterrows is the slowest thing in Pandas — avoid it; vectorize or use map/merge instead.
  • Column arithmetic, np.where, and .map replace most row-wise apply calls.
  • merge (SQL-style join) aligns predictions with labels far faster than lookups in a loop.
  • pivot_table reshapes long logs into wide summaries for comparison.
DEEP DIVE
Pandas performance follows one rule: stay in compiled, columnar operations and out of the Python interpreter. iterrows materializes a Python object per row and is dramatically slower than any vectorized alternative; apply with a Python function along axis=1 is nearly as bad because it too calls back into Python per row. The fix is almost always to express the logic over whole columns: arithmetic on Series, np.where for conditional assignment, and .map with a dict for lookups all run in C. When you need to combine two datasets — predictions with ground-truth labels, say — a merge is both faster and more correct than looking each row up in a loop, because it aligns on keys in one hashed pass and makes the join type (inner, left) explicit so unmatched rows are handled deliberately rather than silently. And when you need to compare across a dimension — accuracy per model per day — pivot_table reshapes a long event log into a compact grid in one call. The habit to build: whenever you reach for a loop or a row-wise apply, pause and find the vectorized column expression, the merge, or the pivot that does the same thing.

Vectorized Pandas is how you'll compute evaluation metrics over large result sets and assemble feature tables — at a scale where the async and batching patterns in Pillar 2 also start to matter. Speed here compounds across every data step.
PD4Joins, Merges & Reshaping in Depth Applied
Combining datasets correctly is deceptively hard. Mastering merge join types, concat, and the long↔wide reshaping verbs (pivot, melt) is what lets you assemble evaluation tables, join predictions to labels, and reshape logs without dropping or duplicating rows.
WHY THIS MATTERS
Joining model predictions to ground truth, stitching per-day log files together, reshaping a long event log into a model×metric grid — each needs the right join type or reshape verb. The wrong one silently loses rows or multiplies them, quietly corrupting every metric downstream.
KEY POINTS
  • merge join types: inner (matches only), left (keep left), outer (keep all) — choose deliberately.
  • Watch cardinality: a non-unique join key causes a many-to-many explosion in row count.
  • concat stacks frames vertically (more rows) or horizontally (more columns).
  • melt goes wide→long; pivot/pivot_table goes long→wide.
DEEP DIVE
Combining data is where silent corruption most often enters an analysis, so it rewards deliberate care. A merge aligns two frames on a key, and the join type decides what happens to non-matching rows: an inner join keeps only keys present in both (dropping unmatched rows from each side), a left join keeps every row of the left frame and fills unmatched right columns with NaN, and an outer join keeps everything. Choosing the wrong one silently changes your row set — an inner join that you expected to be lossless quietly deletes predictions that lacked a label, skewing every metric computed afterward. The subtler trap is cardinality: merge pairs every matching row on the left with every matching row on the right, so if the join key isn't unique on one side you get a many-to-many explosion that multiplies rows and inflates counts. The defensive habit is to check row counts before and after, and to confirm key uniqueness when you expect a one-to-one or one-to-many join. concat is the other combiner — stacking frames vertically to add rows (assembling per-day logs) or horizontally to add columns. Reshaping is the complementary skill: melt collapses many columns into key-value rows (wide to long), and pivot/pivot_table spreads a long event log into a grid (long to wide), which is how you turn a stream of per-request records into a compact model-by-metric comparison table.

TY1Type Hints & Why They Matter for AI Code Foundations Start here
Type hints turn Python into a checkable language. In AI systems that pass dicts, tensors, and API responses between many functions, types are the cheapest way to catch the shape-and-key mistakes that otherwise blow up at runtime deep in a pipeline.
WHY THIS MATTERS
An LLM response is a nested structure; an embedding is a specific shape; a tool call has a fixed schema. When these flow through ten functions, a wrong key or a swapped argument surfaces far from its cause. Type hints plus a checker catch these before you run.
KEY POINTS
  • Hints annotate parameters and returns: def f(x: int) -> str: — they don't change runtime behavior.
  • Containers are parameterized: list[float], dict[str, int], tuple[int, ...].
  • Optional[X] (a.k.a. X | None) documents nullable values explicitly.
  • A static checker (mypy, pyright) verifies hints; the interpreter ignores them.
INSTALL
pip install mypy
DEEP DIVE
Python's type hints are annotations that a separate tool checks — the interpreter itself never enforces them, which is exactly why they're safe to add incrementally to any codebase. Their value in AI code is disproportionate because so much of the work is plumbing structured data between functions: a retrieval function returns a list of chunk dicts, an assembly function turns those into a prompt payload, an API wrapper returns a typed response. Each handoff is a chance to pass the wrong shape or misname a key, and without types those errors travel silently until something downstream indexes into a structure that isn't what it assumed. Annotating the boundaries — what each function takes and returns — lets a static checker like mypy or pyright trace the data flow and flag mismatches before you run a single request, which matters most precisely when the failure would otherwise happen after an expensive model call. Parameterized containers (list[float] for an embedding, dict[str, str] for a header map) document intent precisely, and Optional forces you to acknowledge the cases where a value might be missing rather than discovering it via an AttributeError on None.

WHY THIS MATTERS

  • Dataclasses give structure and IDE support but don't validate types at runtime.
  • Pydantic models validate and coerce on construction — ideal for untrusted input (LLM output, API payloads).

There's a spectrum from raw dicts to fully validated models, and knowing where to sit on it is a production skill. A dict is flexible but opaque — nothing tells you what keys it should have, and a typo becomes a KeyError three functions later. AS1Async & Concurrency for I/O-Bound AI Work Core
AI apps spend most of their time waiting on network I/O — API calls, DB queries, tool invocations. async/await lets one thread wait on many calls at once, turning a sequence of slow requests into concurrent ones. This is the single biggest latency win in LLM applications.
WHY THIS MATTERS
You need embeddings for 100 chunks, or answers from 5 sub-agents, or three tool calls the model requested. Done sequentially that's the sum of every latency; done concurrently with async it's roughly the slowest single call. For user-facing AI, that's the difference between snappy and sluggish.
KEY POINTS
  • async def defines a coroutine; await yields control while waiting on I/O.
  • asyncio.gather runs many coroutines concurrently and collects results in order.
  • Async helps I/O-bound work (network, disk), not CPU-bound math — that's what NumPy/threads/processes are for.
  • A semaphore caps concurrency so you don't blow past API rate limits.
DEEP DIVE
Almost everything an LLM application does is wait: it sends a request to an API and sits idle for hundreds of milliseconds until the response comes back. Synchronous code does these waits one after another, so ten calls take ten times as long as one. Async changes the model — a coroutine, defined with async def, runs until it hits an await on an I/O operation, at which point it yields control back to the event loop, which starts or resumes other coroutines while the first waits. The result is that a single thread can have dozens of API calls in flight simultaneously, and the total time collapses toward the duration of the slowest one instead of the sum of all. asyncio.gather is the workhorse: hand it a list of coroutines and it runs them concurrently and returns their results in the original order. The crucial caveat is that async only helps I/O-bound work — time spent waiting on the network or disk. It does nothing for CPU-bound computation like large matrix math, which blocks the event loop; that's NumPy's or a process pool's job. And because concurrency is now easy, you need a governor: a semaphore limits how many coroutines run at once so you respect API rate limits instead of firing 500 requests in the same instant and getting throttled.
pythonasync_calls.py
import asyncio, random

async def embed(text: str, sem: asyncio.Semaphore) -> list[float]:
    """Simulate an I/O-bound embedding API call, rate-limited by a semaphore."""
    async with sem:                       # cap concurrency
        await asyncio.sleep(random.uniform(0.1, 0.3))   # network wait
        return [float(len(text))]         # stand-in vector

async def embed_all(texts: list[str]) -> list[list[float]]:
    sem = asyncio.Semaphore(10)           # at most 10 in flight
    coros = [embed(t, sem) for t in texts]
    return await asyncio.gather(*coros)   # concurrent; results in order

async def main():
    texts = [f"chunk {i}" for i in range(50)]
    vecs = await embed_all(texts)         # ~slowest call, not the sum
    print(f"embedded {len(vecs)} chunks concurrently")

asyncio.run(main())
COMMON PITFALL
Putting heavy CPU work (a big NumPy op, JSON parsing of huge payloads) directly in a coroutine blocks the entire event loop, freezing every other concurrent task. Keep coroutines I/O-only; offload CPU-bound work to asyncio.to_thread or a process pool.
HOW IT CONNECTS
Async is the backbone of the LLM pillar: concurrent embedding, parallel sub-agent calls, and batched requests all build on gather plus a semaphore. Combined with the retry logic in LL2, it's how production LLM code stays both fast and resilient.
ER1Error Handling & Custom Exceptions Core
Robust AI systems fail loudly, specifically, and recoverably. That means catching narrow exceptions (not bare except), raising your own typed exceptions at boundaries, and using try/finally or context managers so resources always get cleaned up.
WHY THIS MATTERS
An LLM call can fail a dozen ways — network, rate limit, malformed JSON, schema mismatch. Handling each specifically (and letting genuine bugs propagate) is what separates a pipeline that degrades gracefully from one that either crashes on everything or silently swallows real problems.
KEY POINTS
  • Catch the narrowest exception that fits; a bare except: hides bugs and swallows KeyboardInterrupt.
  • Define custom exceptions to signal domain failures (e.g. RetrievalError) distinctly from generic ones.
  • raise ... from e preserves the original cause in the traceback (exception chaining).
  • finally and context managers (with) guarantee cleanup even when an error fires.
DEEP DIVE
Good error handling is about precision and honesty. The precision comes from catching the narrowest exception that corresponds to a situation you actually know how to handle — a TimeoutError you can retry, a ValidationError you can reject — and letting everything else propagate. A bare except: is the opposite of precision: it catches every exception including KeyboardInterrupt and genuine programming bugs, converting a clear crash into a silent malfunction that surfaces somewhere confusing later. The honesty comes from custom exceptions. When your retrieval layer fails, raising a domain-specific RetrievalError rather than letting a raw KeyError escape tells every caller exactly what went wrong in your terms, and lets them decide how to respond without reverse-engineering a low-level traceback. Chaining with raise NewError(...) from original keeps both stories — your high-level meaning and the underlying cause — visible in the traceback, which is invaluable when debugging production. Finally, cleanup must be guaranteed regardless of success or failure: a finally block or, better, a context manager ensures a file is closed, a connection released, or a lock freed even when an exception fires mid-operation. Together these make failures informative and safe instead of mysterious and lossy.

class RetrievalError(Exception):
    """Raised when the retrieval layer cannot return usable context."""

class LLMError(Exception):
    """Raised when the model call fails after retries."""

def retrieve(query: str, index) -> list[dict]:
    try:
        hits = index.search(query, k=5)
    except ConnectionError as e:
        # translate a low-level failure into a domain-specific one, keep the cause
        raise RetrievalError(f"vector store unreachable for {query!r}") from e
    if not hits:
        raise RetrievalError(f"no chunks found for {query!r}")
    return hits

    try:
        chunks = retrieve(query, index)
    except RetrievalError:
        return "I couldn't find relevant information to answer that."  # graceful
    # only genuinely transient LLM errors should be caught; bugs propagate
    resp = client.messages.create(model="claude-sonnet-4-6", max_tokens=400,
                                  messages=[{"role": "user", "content": query}])
    return resp.content[0].text

Catch specific exceptions, and never silence one without logging it.
HOW IT CONNECTS
Custom exceptions and precise catching are what make the retry logic (LL2) and the pipeline stages (Pillar 4) composable — each layer raises meaningful failures that the next layer can handle or propagate. Logging (ER2) is the other half: catch specifically, then record what happened.
ER2Logging & Observability Core
print doesn't scale. Structured logging with levels, context, and (ideally) JSON output is how you see what an AI system is doing in production — which prompts, which latencies, which failures — without drowning in noise or leaking secrets.
WHY THIS MATTERS

CO1Threads vs Processes vs Async — Choosing a Model Core Start here
Python has three concurrency models and using the wrong one is a common performance trap. The choice hinges on one question: is the work I/O-bound (waiting on network/disk) or CPU-bound (heavy computation)? The GIL makes this decision consequential.
WHY THIS MATTERS
Embedding 10k documents (I/O-bound API calls) wants async or threads; running a heavy NumPy transform over a huge array (CPU-bound) wants processes. Pick wrong — threads for CPU work — and the GIL means you get zero speedup and added complexity for nothing.
KEY POINTS
  • The GIL lets only one thread run Python bytecode at a time — so threads don't speed up CPU-bound Python.
  • I/O-bound work (API calls, file/DB I/O): use async (many tasks, one thread) or a thread pool.
  • CPU-bound work (big pure-Python or per-element computation): use processes to get real parallelism.
  • Vectorized NumPy/BLAS already releases the GIL and uses multiple cores — often the best answer of all.
DEEP DIVE
Python's Global Interpreter Lock (GIL) permits only one thread to execute Python bytecode at any instant, and that single fact drives the whole concurrency decision. For CPU-bound work — computation that keeps the interpreter busy — threads give no speedup, because the GIL serializes them; you need separate processes, each with its own interpreter and GIL, to actually use multiple cores. For I/O-bound work — where the program spends its time waiting on the network or disk rather than computing — the GIL is irrelevant, because a waiting task isn't holding it; here you want concurrency that overlaps the waits, which is what async (many coroutines cooperatively multiplexed on one thread) and thread pools both provide. So the decision procedure is: first classify the work. If it's waiting on I/O, reach for async (best for large numbers of network calls, like embedding thousands of documents) or a thread pool (simplest when you have blocking library calls). If it's genuine computation, reach for processes. And there's an important escape hatch specific to AI work: heavy numeric operations in NumPy, PyTorch, or BLAS run in C, release the GIL while they compute, and already parallelize across cores internally — so the fastest answer to 'this matrix math is slow' is usually to vectorize it, not to add Python-level concurrency around a slow loop. Matching the model to the workload is the difference between a real speedup and added complexity that buys nothing.
pythonconcurrency_models.py
import asyncio, time
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

# I/O-BOUND -> threads overlap the waits (GIL released during I/O)
def fetch(url: str) -> int:
    time.sleep(0.2)                 # stand-in for a network call
    return len(url)

def fetch_all(urls: list[str]) -> list[int]:
    with ThreadPoolExecutor(max_workers=10) as pool:
        return list(pool.map(fetch, urls))   # ~0.2s total, not 0.2 * n

# CPU-BOUND -> processes for real parallelism (each has its own GIL)
def heavy(n: int) -> int:
    return sum(i * i for i in range(n))       # pure-Python compute

def heavy_all(sizes: list[int]) -> list[int]:
    with ProcessPoolExecutor() as pool:
        return list(pool.map(heavy, sizes))   # uses multiple cores

# I/O-BOUND at scale -> async (thousands of calls, one thread)
async def afetch(url: str) -> int:
    await asyncio.sleep(0.2)
    return len(url)

async def afetch_all(urls: list[str]) -> list[int]:
    return await asyncio.gather(*(afetch(u) for u in urls))
COMMON PITFALL

And spinning up processes for tiny tasks costs more in overhead than it saves. Classify the work first, and remember vectorized NumPy often beats any Python-level concurrency.

IT1Iterators, Generators & Lazy Evaluation Core
Generators produce values one at a time instead of building a whole list in memory. For AI data — streaming a huge file, paginating an API, processing a dataset too big for RAM — lazy evaluation is what makes the work possible at all.
WHY THIS MATTERS
You need to process a 50 GB JSONL dataset, or every page of a paginated API, or a stream of documents to embed. Loading it all into a list would exhaust memory; a generator yields one record at a time, so memory stays flat no matter how large the source.
KEY POINTS
  • A generator function uses yield to produce values lazily, one per next(), keeping state between calls.
  • Generators are iterators: consumed once, memory-flat, ideal for large or infinite streams.
  • Generator expressions (x for x in it) are lazy comprehensions — no intermediate list.
  • Chain generators into pipelines: each stage pulls from the previous, processing one item at a time.
DEEP DIVE
A generator inverts the usual relationship between producing and consuming data. A normal function that returns a list computes every value up front and holds them all in memory; a generator function, marked by yield, produces one value each time it's asked, suspends its execution with all local state intact, and resumes where it left off on the next request. This laziness is transformative for AI data work, where sources are routinely larger than RAM. Reading a 50 GB JSONL file line by line as a generator keeps memory flat — you hold one record at a time, not fifty gigabytes. Paginating an API becomes a generator that yields records and fetches the next page only when the current one is exhausted, so a caller can iterate a million results without ever materializing them. Generator expressions bring the same laziness to comprehension syntax: (transform(x) for x in source) builds no intermediate list, it just describes a stream. The real elegance emerges when you chain generators into a pipeline — parse, then filter, then batch — where each stage pulls one item from the stage before it, so the whole pipeline processes a single record end to end before touching the next, and memory never grows with the size of the input. The one caveat to respect is that a generator is consumed exactly once; iterating it a second time yields nothing, because its state is exhausted.
pythongenerators.py
import json
from typing import Iterator

# Lazily stream a huge JSONL file - one record in memory at a time
def read_jsonl(path: str) -> Iterator[dict]:
    with open(path) as f:
        for line in f:                     # file iteration is itself lazy
            line = line.strip()
            if line:
                yield json.loads(line)     # produce one record, then pause

# Lazily paginate an API without materializing all results
def paginate(fetch_page, page_size: int = 100) -> Iterator[dict]:
    page = 0
    while True:
        batch = fetch_page(page, page_size)
        if not batch:
            return                         # stop the generator
        yield from batch                   # yield each item in the page
        page += 1

# Chain generators into a memory-flat pipeline
def pipeline(path: str) -> Iterator[str]:
    records = read_jsonl(path)                          # stage 1: parse
    valid   = (r for r in records if r.get("text"))     # stage 2: filter (lazy)
    return (r["text"].strip() for r in valid)           # stage 3: extract (lazy)

DV1Robust File & JSON I/O Core Start here
Data enters AI systems as files — CSV, JSON, JSONL, Parquet — and real-world files are messy. Reading them robustly (right encoding, streaming when large, malformed lines handled) is the unglamorous foundation that everything downstream depends on.
WHY THIS MATTERS
Your training data, eval sets, and document corpora arrive as files that are too big for memory, encoded inconsistently, or contain the occasional malformed line. Handling these deliberately — not assuming clean UTF-8 that fits in RAM — is what keeps ingestion from failing at 2 a.m. on record 4 million.
KEY POINTS
  • Always open text with an explicit encoding="utf-8"; never rely on the platform default.
  • Use pathlib.Path for paths — portable, readable, and safe across OSes.
  • For large data, stream line by line (JSONL) rather than json.load-ing a giant file.
  • Handle malformed lines per-record so one bad row doesn't abort the whole ingest.
DEEP DIVE
File I/O looks trivial until it meets real data, at which point three assumptions routinely break and take your pipeline with them. The first is encoding: text files are not always UTF-8, and relying on the platform default means the same code reads correctly on your machine and throws a UnicodeDecodeError on a server with a different locale — so you always specify encoding="utf-8" explicitly (and decide deliberately how to handle bytes that don't decode). The second is size: a single json.load on a multi-gigabyte file reads the whole thing into memory and can exhaust RAM, which is exactly why the JSONL format — one JSON object per line — dominates AI datasets: it lets you stream, parsing and processing one record at a time with flat memory, as a generator. The third is cleanliness: at scale, some fraction of lines will be malformed — a truncated write, an encoding glitch, a stray character — and the naive approach where one bad line aborts the entire ingest is unacceptable when you're four million records deep. The robust pattern wraps per-record parsing in a try/except that logs and skips the bad line while continuing, so a handful of corrupt records cost you those records rather than the whole run. Using pathlib.Path throughout keeps path handling portable and readable. None of this is glamorous, but ingestion is the layer where a huge share of real AI-pipeline failures actually happen.
pythonfile_io.py
import json
from pathlib import Path
from typing import Iterator

def stream_jsonl(path: str | Path) -> Iterator[dict]:
    """Stream a JSONL file robustly: explicit encoding, skip malformed lines."""
    path = Path(path)
    bad = 0
    with path.open(encoding="utf-8") as f:      # explicit encoding, always
        for lineno, line in enumerate(f, 1):
            line = line.strip()
            if not line:
                continue
            try:
                yield json.loads(line)          # one record at a time
            except json.JSONDecodeError:
                bad += 1                         # skip, don't abort
                if bad <= 5:
                    print(f"  skipped malformed line {lineno}")
    if bad:
        print(f"  total malformed lines skipped: {bad}")

# Writing JSONL incrementally (also memory-flat)
def write_jsonl(path: str | Path, records: Iterator[dict]) -> int:
    n = 0
    with Path(path).open("w", encoding="utf-8") as f:
        for rec in records:
            f.write(json.dumps(rec, ensure_ascii=False) + "\n")
            n += 1
    return n
COMMON PITFALL

DV2Validation Pipelines for Messy Data Applied
Raw data is untrusted until validated. A validation pipeline parses each record against a schema (Pydantic), separates the good from the bad, and reports what it rejected — so downstream code works only with data it can trust, and you can see what was dropped and why.
WHY THIS MATTERS
Before embedding a corpus or training on a dataset, each record needs the right fields, types, and ranges. A validation pipeline turns a messy input stream into a clean, typed stream plus a rejects report — so you catch data problems up front instead of getting garbage predictions and tracing them back for hours.
KEY POINTS
  • Define the expected shape once as a Pydantic model; validate every record against it.
  • Partition the stream: valid typed records proceed; invalid ones go to a rejects list with reasons.
  • Report validation stats (accepted / rejected / why) so data quality is visible, not hidden.
  • Validate at the boundary, then pass typed objects inward — the core code trusts its input.
DEEP DIVE
A validation pipeline operationalizes a single principle: data is untrusted until proven otherwise, and the proof happens once, at the boundary. Rather than sprinkling defensive checks throughout your code — is this field present, is it the right type, is the value in range — you define the expected shape one time as a Pydantic model and run every incoming record through it. Each record either validates, producing a typed object your downstream code can use with complete confidence, or it fails, and here's the key design choice: a failure should not crash the pipeline and should not vanish silently. Instead you partition the stream — valid records flow onward as typed objects, invalid records go to a rejects collection tagged with the reason they failed — so the pipeline is resilient to bad data and, just as importantly, transparent about it. That transparency is what makes data quality observable: at the end you can report how many records were accepted, how many rejected, and why, which turns 'the model's predictions are weirdly bad' into 'thirty percent of the input failed the amount-must-be-positive check.' Validating at the boundary and passing typed objects inward also simplifies everything downstream, because the core logic never has to wonder whether a field might be missing or a string might actually be a number — the model guaranteed it. This is the data-layer expression of the same edge-validation discipline you apply to LLM output and tool calls.

from pydantic import BaseModel, Field, ValidationError
from typing import Iterator
from dataclasses import dataclass, field

class Record(BaseModel):
    id: str = Field(min_length=1)
    text: str = Field(min_length=1)
    amount: float = Field(ge=0)              # must be non-negative
    label: str

@dataclass
class Report:
    accepted: list[Record] = field(default_factory=list)
    rejected: list[tuple[dict, str]] = field(default_factory=list)
    def summary(self) -> str:
        n = len(self.accepted) + len(self.rejected)
        return f"{len(self.accepted)}/{n} accepted, {len(self.rejected)} rejected"

def validate_stream(records: Iterator[dict]) -> Report:
    report = Report()
    for raw in records:
        try:
            report.accepted.append(Record(**raw))     # validate + coerce
        except ValidationError as e:
            reason = "; ".join(err["msg"] for err in e.errors())
            report.rejected.append((raw, reason))      # keep it, with the reason
    return report

from anthropic import Anthropic

client = Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])  # from env, not source

        max_tokens: int = 512) -> str:

    response = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=max_tokens,

    )

LL2Retries, Timeouts & Rate Limits Resilience
Network calls fail, models get overloaded, and rate limits bite. Production LLM code wraps every call in retry with exponential backoff, sane timeouts, and rate-limit awareness — so a transient error becomes a brief pause instead of a user-facing failure.
WHY THIS MATTERS
At any real volume you'll hit 429s (rate limit) and 529s (overloaded) and occasional network blips. Without retries, each one is a failed request; with exponential backoff and jitter, the vast majority recover invisibly. This is the difference between a demo and a service.
KEY POINTS
  • Exponential backoff waits 1s, 2s, 4s… between retries so you don't hammer a struggling API.
  • Jitter (a random offset) prevents synchronized retries from all clients at once.
  • Retry only transient errors (429, 5xx, timeouts) — not 4xx bugs like a bad request.
  • Set an explicit timeout so a hung call fails fast instead of blocking forever.
DEEP DIVE
Any system that calls an external API at volume must treat failure as normal, not exceptional. Three failure modes dominate LLM calls: rate limits (HTTP 429) when you exceed your quota, overload (529) or server errors (5xx) when the service is under strain, and network timeouts when a call hangs. The correct response to all three is the same — wait and retry — but the waiting must be done carefully. Exponential backoff increases the delay between attempts (1s, then 2s, then 4s) so that if the service is struggling you back off rather than piling on. Jitter adds a small random component to each delay, which matters at scale because without it every client that failed at the same instant retries at the same instant, creating a synchronized thundering herd that re-overloads the service. Crucially, retries must be scoped to transient errors only: a 429 or a 503 is worth retrying, but a 400 (malformed request) or 401 (bad key) is a bug in your code that will fail identically every time, so retrying it just wastes time and hides the real problem. A timeout is the other half of resilience — without an explicit one, a hung connection blocks a worker indefinitely; with one, it fails fast and enters the retry loop. Together these turn the messy reality of network calls into a service that mostly just works.

import time, random
from anthropic import Anthropic, APIStatusError, APITimeoutError

client = Anthropic(timeout=30.0)             # fail a hung call fast

TRANSIENT = {429, 500, 502, 503, 529}        # worth retrying

def ask_resilient(prompt: str, max_retries: int = 5) -> str:
    for attempt in range(max_retries):
        try:
            resp = client.messages.create(
                model="claude-sonnet-4-6", max_tokens=512,
                messages=[{"role": "user", "content": prompt}],
            )
            return resp.content[0].text
        except APIStatusError as e:
            if e.status_code not in TRANSIENT:
                raise                        # a real bug (e.g. 400) - don't retry
            wait = 2 ** attempt + random.uniform(0, 1)   # backoff + jitter
            time.sleep(wait)
        except APITimeoutError:
            time.sleep(2 ** attempt + random.uniform(0, 1))
    raise RuntimeError(f"failed after {max_retries} attempts")
COMMON PITFALL
Retrying non-transient errors (like a 400 bad request or 401 auth failure) is worse than not retrying — it delays the inevitable failure and can mask the real bug behind a confusing timeout. Always check the status code and re-raise anything that isn't genuinely transient.
HOW IT CONNECTS

LL3Tool Use & Structured Outputs Core
Real agents don't just chat — they call tools and return structured data. The pattern: describe your tools with a JSON schema, let the model decide when to call them, execute the call, and feed the result back. Validating that structured output is where Pydantic earns its keep.
WHY THIS MATTERS
A refund agent needs to look up an order, check a policy, and issue a refund — each a typed function call, not free text. Tool use is how the model reaches into your systems safely; structured outputs are how you get back data you can act on programmatically instead of parsing prose.
KEY POINTS
  • You describe tools with a name, description, and JSON-schema input; the model chooses when to invoke them.
  • The response contains tool_use blocks with the chosen tool and validated-shape arguments.
  • You execute the tool, then return a tool_result so the model can continue with the data.
  • Validate tool arguments with Pydantic before executing — never trust the shape blindly.
DEEP DIVE
Tool use turns a language model from a text generator into something that can act, and the pattern is a clean loop worth internalizing. You give the model a set of tools, each described by a name, a natural-language description of when to use it, and a JSON schema for its inputs. The model, given a task, decides whether and which tool to call, and if it does, the response comes back not as prose but as a structured tool_use block naming the tool and supplying arguments that conform to your schema. Your code then executes the actual function — query the database, call the internal API — and returns the outcome as a tool_result block in a follow-up message, at which point the model incorporates the real data and continues, perhaps calling another tool or producing a final answer. The schema is doing double duty: it steers the model toward well-formed calls and it documents the contract, but it is not a guarantee, which is why the production discipline is to validate the arguments with Pydantic at the moment you receive them, before you execute anything with side effects. Structured outputs are the same idea pointed at the final answer — instead of parsing facts out of a paragraph, you ask the model to fill a schema, then validate it, so downstream code receives typed data it can act on directly.

    return resp.content[0].text                    # no tool -> plain answer

Tool use plus validated structured output is the foundation of the agent patterns in your LangGraph and agentic labs — the same describe-decide-execute-return loop, just orchestrated across many steps. Pydantic (TY2) is what makes it safe; async (AS1) is what makes parallel tool calls fast.
LL4Streaming & Token-Budget Awareness Applied
For anything user-facing, streaming the response token-by-token transforms perceived latency — words appear immediately instead of after a long pause. Pair it with token-budget awareness so long contexts don't silently overflow or run up cost.
WHY THIS MATTERS
A user watching a blank screen for five seconds feels broken; the same five seconds with text streaming feels fast. And when you assemble long RAG contexts, knowing your token budget prevents truncated prompts and surprise bills. Both are table stakes for a real product.
KEY POINTS
  • Streaming yields incremental text events you can render as they arrive — huge perceived-latency win.
  • The final message still carries usage (input/output tokens) for cost and budget tracking.
  • Every model has a context window; assembled prompt + expected output must fit inside it.
  • Count tokens when building long contexts so you trim deliberately instead of getting truncated.
DEEP DIVE
Two related concerns separate a polished LLM feature from a rough one: how the response reaches the user, and how you manage the finite context budget. Streaming addresses the first. A model generates tokens sequentially, and by default you wait for all of them before seeing anything; with streaming, the API emits each chunk as it's produced and you render it immediately, so the user sees words appear within a fraction of a second. The total generation time is identical, but perceived latency drops dramatically because the wait is filled with visible progress — for any interactive interface this is the single highest-leverage UX change you can make. The second concern is the token budget. Every model has a fixed context window, and your assembled prompt plus the space reserved for the output must fit within it. In RAG especially, where you're stuffing retrieved chunks into the prompt, it's easy to overflow — and an overflow either errors or silently truncates, dropping exactly the context you carefully retrieved. The fix is to count tokens as you assemble, so you trim or prioritize deliberately rather than discovering the limit by accident. The usage data returned with each response closes the loop: it reports input and output token counts, which is what you track for cost and for tuning how much context you can afford to include.

from anthropic import Anthropic

client = Anthropic()

def ask_streaming(prompt: str, max_tokens: int = 512) -> str:
    """Stream tokens as they arrive; return the full text at the end."""
    pieces: list[str] = []
    with client.messages.stream(
        model="claude-sonnet-4-6", max_tokens=max_tokens,
        messages=[{"role": "user", "content": prompt}],
    ) as stream:
        for text in stream.text_stream:      # incremental chunks
            print(text, end="", flush=True)  # render immediately
            pieces.append(text)
        final = stream.get_final_message()   # carries usage for budgeting
    print()
    print(f"[tokens] in={final.usage.input_tokens} out={final.usage.output_tokens}")
    return "".join(pieces)

Assembling a long context without counting tokens leads to silent truncation — the model drops the overflow, often the very chunks you retrieved, and answers from partial context with no error. Budget the prompt against the context window explicitly, reserving room for the output, before you send.
HOW IT CONNECTS
Streaming is the delivery layer over the LL1 client and LL2 retries; token budgeting connects straight back to the context-assembly and chunking work in your RAG labs. Together they make an LLM feature feel fast and stay within cost and context limits — the finishing polish on the whole stack.
LL5Embeddings API & Batching Core
Retrieval starts with embeddings. Calling an embeddings API efficiently means batching many texts per request, handling the response order, and combining it with the async and retry patterns so you can embed a large corpus quickly and reliably.
WHY THIS MATTERS
Embedding a 100k-document corpus one API call at a time is slow and expensive. Batching dozens of texts per request, running batches concurrently, and retrying transient failures turns an hours-long job into minutes — and is the standard way every production ingestion pipeline builds its vector index.
KEY POINTS
  • Send many texts per request (a batch) instead of one call per text — far fewer round-trips.
  • Preserve order: the response embeddings line up with your input list positions.
  • Combine batching with async gather + a semaphore to run batches concurrently within rate limits.
  • Normalize embeddings once at ingestion (NP3) so retrieval is a plain dot product.
DEEP DIVE
Embedding a corpus is the ingestion half of retrieval, and doing it efficiently is mostly about amortizing network round-trips. Every API call has fixed overhead — connection, request, latency — so calling an embeddings endpoint once per document is enormously wasteful when the endpoint accepts a batch of texts in a single request. Batching dozens or hundreds of texts per call collapses that overhead, and the response returns embeddings in the same order as your input, so you can zip them back to their source records by position. That handles throughput within a request; to scale across the whole corpus you layer on the concurrency patterns from earlier — run multiple batches at once with asyncio.gather, bounded by a semaphore so you stay inside rate limits, and wrap each call in the retry-with-backoff logic so transient failures self-heal. The last piece is a small optimization with big downstream payoff: normalize each embedding to unit length once, at ingestion time, so that at query time similarity is a plain dot product (as in NP3) rather than a full cosine computation per comparison. Put together — batch to amortize round-trips, concurrency to parallelize batches, retries for reliability, normalize once — this is precisely how a production pipeline turns a large document set into a searchable vector index in a fraction of the naive time.
pythonembed_corpus.py
import asyncio, numpy as np

async def embed_batch(texts: list[str], client, sem) -> list[list[float]]:
    """Embed a batch of texts in ONE request, rate-limited, with retry."""
    async with sem:
        for attempt in range(5):
            try:
                # resp = await client.embeddings.create(model=..., input=texts)
                # return [d.embedding for d in resp.data]     # order preserved
                await asyncio.sleep(0.05)                       # stand-in
                return [[float(len(t))] * 384 for t in texts]
            except Exception:
                await asyncio.sleep(2 ** attempt)
        raise RuntimeError("embedding batch failed")

async def embed_corpus(texts: list[str], client, batch_size: int = 64):
    sem = asyncio.Semaphore(8)                     # 8 concurrent batches
    batches = [texts[i:i+batch_size] for i in range(0, len(texts), batch_size)]
    results = await asyncio.gather(*(embed_batch(b, client, sem) for b in batches))
    vecs = [v for batch in results for v in batch]  # flatten, order preserved
    arr = np.asarray(vecs, dtype=np.float32)
    norms = np.linalg.norm(arr, axis=1, keepdims=True)
    return arr / np.clip(norms, 1e-12, None)        # normalize once at ingestion
COMMON PITFALL
Losing the mapping between input texts and returned embeddings — by processing batches out of order without tracking positions — silently misaligns vectors with their source documents, so retrieval returns the wrong chunks with no error. Preserve order explicitly when flattening concurrent batch results.
HOW IT CONNECTS
This is the ingestion counterpart to NP3's retrieval math, built on the async/semaphore pattern (AS1), retries (LL2), and clean data streams (DV1–DV2). The normalized array it produces is the vector index that cosine search queries.
LL6Caching LLM & Embedding Calls Performance
Model calls are slow and cost money, and much work is repeated — the same query, the same chunk embedded twice. Caching results keyed by a hash of the input eliminates duplicate calls, cutting latency and cost dramatically in any real workload.
WHY THIS MATTERS
During development you re-run the same prompts constantly; in production, common queries and re-embedded documents repeat. A content-hash cache means identical inputs return instantly and for free instead of hitting the API again — often the single biggest cost and latency saving in an LLM system.
KEY POINTS
  • Key the cache on a hash of the exact input (prompt + params, or text for embeddings).
  • functools.lru_cache caches in-process; a dict-on-disk or Redis persists across runs.
  • Cache deterministic-enough calls (embeddings always; completions when temperature is low/zero).
  • Include model and parameters in the key so a config change doesn't return stale results.
DEEP DIVE
Caching is often the highest-leverage optimization in an LLM system because model calls are simultaneously the slowest and most expensive operation, and a surprising amount of work is exactly repeated. The mechanism is simple: before making a call, compute a key from the precise inputs — for an embedding, a hash of the text; for a completion, a hash of the prompt plus the parameters that affect the output — and check whether you've already computed and stored the result for that key. If so, return it instantly and for free; if not, make the call and store it. The subtlety is entirely in the key. It must capture everything that changes the output: not just the prompt but the model name and the generation parameters, because otherwise switching models or temperature would silently return stale results computed under the old configuration. What's safe to cache depends on determinism — embeddings for a given text are stable and always cacheable; completions are cacheable when temperature is low or zero so the same input reliably yields the same output, and less so when you deliberately want varied generations. The implementation scales with your needs: functools.lru_cache gives you an in-process cache for a single run (great for development and for hot paths within a request), while a persistent store — a dict pickled to disk, or Redis — carries results across runs and processes, which is what turns 're-embedding the whole corpus every deploy' into 're-embedding only what changed.'

import hashlib, json, functools

def _key(*parts) -> str:
    """Stable hash of all inputs that affect the output."""
    blob = json.dumps(parts, sort_keys=True, default=str)
    return hashlib.sha256(blob.encode()).hexdigest()

# In-process cache for a hot function (one run)
@functools.lru_cache(maxsize=10_000)
def embed_cached(text: str, model: str = "embed-v1") -> tuple:
    # ... real embedding call here ...
    return tuple([float(len(text))] * 8)          # tuple so it's hashable

# Persistent cache (across runs) keyed on prompt + params + model
class DiskCache:
    def __init__(self): self.store: dict[str, str] = {}   # swap for Redis/shelve
    def ask(self, client, prompt: str, model: str, temperature: float) -> str:
        key = _key(prompt, model, temperature)     # model + params in the key!
        if key in self.store:
            return self.store[key]                 # hit: instant, free
        resp = client.messages.create(model=model, max_tokens=400,
                   temperature=temperature,
                   messages=[{"role": "user", "content": prompt}])
        text = resp.content[0].text
        self.store[key] = text
        return text
COMMON PITFALL
Omitting the model or parameters from the cache key returns stale results after a config change — you switch models or lower the temperature but keep getting the old cached output, a bug that's maddening to track down. Always fold every output-affecting input into the key, and only cache completions when they're deterministic enough to reuse.
HOW IT CONNECTS
Caching sits in front of the LL1 client, LL5 embeddings, and every retrieval call, multiplying the gains from async and batching. In development it makes iteration instant; in production it's frequently the largest single reduction in both latency and API cost.
LL7RAG Context Assembly Under a Token Budget Applied
Retrieval gives you candidate chunks; assembly turns them into a prompt that fits the token budget and puts the model in the best position to answer. This is where token counting, ordering, deduplication, and truncation come together — the craft between retrieval and generation.
WHY THIS MATTERS
You retrieved 20 chunks but only 6 fit the budget alongside the question and room for the answer. Which 6, in what order, deduplicated how? Good assembly is the difference between an answer grounded in the right context and one that's truncated, redundant, or missing the key passage.
KEY POINTS
  • Reserve budget for the system prompt, the question, and the expected output — fill the rest with chunks.
  • Add chunks highest-score-first until the next one won't fit; count tokens as you go.
  • Deduplicate near-identical chunks so you don't waste budget on repetition.
  • Order deliberately (most relevant prominent) and label chunks so the model can cite them.
DEEP DIVE
Context assembly is the connective craft between retrieval and generation, and it's where a RAG system is won or lost. Retrieval hands you a ranked set of candidate chunks, but you can't simply concatenate them — the model has a finite context window, and the assembled prompt must leave room for the system instructions, the user's question, and crucially the output the model will generate. So assembly begins with budgeting: subtract the fixed costs and the reserved output space from the context window, and what remains is the budget for chunks. You then fill that budget deliberately. Add chunks in descending relevance order, counting tokens as you go, and stop before the chunk that would overflow — a greedy fill that guarantees the most relevant context makes it in. Along the way you deduplicate, because retrieval frequently returns near-identical passages, and spending scarce budget on repetition crowds out genuinely new information. Ordering matters beyond just what's included: models attend unevenly across a long context, so placing the most relevant material where it's prominent, and labeling each chunk so the model can attribute claims to a source, improves both answer quality and citability. The failure mode this prevents is severe and common — dump too much in and the prompt silently truncates, often dropping the very passage that held the answer, so the model responds fluently from incomplete context and no error is ever raised. Deliberate, budget-aware assembly is what makes retrieval actually pay off.
pythonassemble.py
def approx_tokens(text: str) -> int:
    return max(1, len(text) // 4)          # rough; use a real tokenizer in prod

def assemble_context(question: str, chunks: list[dict],
                     context_window: int = 200_000,
                     reserved_output: int = 1024,
                     system_tokens: int = 200) -> str:
    """Fill the token budget with the most relevant, de-duplicated chunks."""
    budget = context_window - reserved_output - system_tokens - approx_tokens(question)
    chunks = sorted(chunks, key=lambda c: c["score"], reverse=True)

    seen_text: set[str] = set()
    selected, used = [], 0
    for c in chunks:
        norm = c["text"].strip().lower()[:200]
        if norm in seen_text:              # dedup near-identical chunks
            continue
        cost = approx_tokens(c["text"])
        if used + cost > budget:           # stop before overflow
            break
        seen_text.add(norm)
        selected.append(c)
        used += cost

    # label chunks so the model can cite them; most relevant first
    blocks = [f"[chunk {i+1} | source={c.get('id','?')}]\n{c['text']}"
              for i, c in enumerate(selected)]
    return "\n\n".join(blocks)
COMMON PITFALL
Concatenating retrieved chunks without a token budget silently overflows the context window — the API truncates the prompt, often dropping the lowest-placed chunks that may hold the answer, and the model answers from partial context with no error. Always budget explicitly and reserve room for the output.
HOW IT CONNECTS
Assembly is the hinge between the retrieval math (NP3), the embeddings pipeline (LL5), and the generation call (LL1) with its streaming and token accounting (LL4). It's the section where the whole stack — data, vectors, budgeting, generation — comes together into an answer.
LL8Structured JSON Output & Prompt Patterns Applied
When you need machine-usable output, ask for structured JSON against a schema and validate it — don't parse prose. Combined with a few durable prompt patterns (clear role, explicit format, few-shot examples), this is how you get reliable, typed results from a generative model.
WHY THIS MATTERS
Classification, extraction, routing, scoring — anything where the next step is code, not a human — needs structured output. Asking for JSON matching a schema and validating it with Pydantic gives you typed data you can act on; a few prompt patterns make the model produce it reliably.
KEY POINTS
  • Ask for JSON conforming to an explicit schema; state the format precisely in the prompt.
  • Validate the returned JSON with Pydantic — never trust the model's shape blindly.
  • Durable prompt patterns: clear role/instructions, explicit output format, and few-shot examples.
  • On a validation failure, you can re-prompt with the error — a self-correcting loop.
DEEP DIVE
When the consumer of a model's output is code rather than a person, free-form prose is the wrong target — you want structured data, and the reliable way to get it is to ask for JSON conforming to an explicit schema and then validate what comes back. The asking is a prompt-engineering task with a few durable patterns behind it. State the role and instructions clearly so the model knows what it's doing; specify the output format precisely, ideally showing the exact JSON shape you expect; and when the task is subtle, include a few examples of input-output pairs (few-shot prompting), which is one of the most effective ways to pin down format and behavior. These patterns are stable across models and tasks and are worth internalizing once. The validating half is non-negotiable: a model instructed to emit JSON usually does, but 'usually' is not 'always,' so you parse the response and validate it against a Pydantic model, which both confirms the structure and coerces types. If validation fails, you're not stuck — because you have a precise error message, you can re-prompt the model with the exact problem ('your JSON was missing the required field X') in a short self-correcting loop that recovers most malformed responses. The result is a pattern that extracts reliable, typed, actionable data from a generative model: classification labels, extracted entities, routing decisions, structured scores — all validated and ready for the code that consumes them, rather than scraped hopefully out of a paragraph.
pythonstructured.py
import json
from pydantic import BaseModel, Field, ValidationError

class Triage(BaseModel):
    category: str = Field(pattern="^(refund|shipping|technical|other)$")
    urgency: int = Field(ge=1, le=5)
    summary: str

SCHEMA_HINT = '''Respond with ONLY a JSON object of this exact shape:
{"category": "refund|shipping|technical|other", "urgency": 1-5, "summary": "..."}'''

def triage(client, ticket: str, max_retries: int = 2) -> Triage:
    prompt = f"{SCHEMA_HINT}\n\nSupport ticket:\n{ticket}"
    last_err = ""
    for _ in range(max_retries + 1):
        content = prompt if not last_err else f"{prompt}\n\nYour last reply was invalid: {last_err}. Return valid JSON."
        resp = client.messages.create(model="claude-sonnet-4-6", max_tokens=300,
                   messages=[{"role": "user", "content": content}])
        try:
            data = json.loads(resp.content[0].text)
            return Triage(**data)                 # validate + coerce -> typed result
        except (json.JSONDecodeError, ValidationError) as e:
            last_err = str(e)                     # feed the error back and retry
    raise ValueError(f"model did not return valid output: {last_err}")
COMMON PITFALL
Parsing facts out of prose with string operations or regexes is brittle — the model rephrases, adds a preamble, or changes order, and your parser breaks. Ask for JSON against a schema and validate it; if you're tempted to regex a model's paragraph, that's the signal to request structured output instead.
HOW IT CONNECTS
Structured output unifies the tool-use pattern (LL3), the Pydantic validation (TY2), and the retry idea (LL2) into the standard way to get actionable data from a model. It's the pattern behind classification, extraction, and routing in every agentic system you'll build.

import asyncio, numpy as np, logging
from pydantic import BaseModel

log = logging.getLogger("rag")

class Doc(BaseModel):
    id: str
    text: str

# --- Stage 1: ingest + validate (DV1/DV2/IT1) ---
def ingest(records) -> list[Doc]:
    docs = []
    for raw in records:                       # records = stream_jsonl(path)
        try: docs.append(Doc(**raw))
        except Exception as e: log.warning(f"skip bad record: {e}")
    log.info(f"ingested {len(docs)} docs")
    return docs

# --- Stage 2: embed in batches + normalize (LL5/NP3/AS1) ---
async def build_index(docs: list[Doc], embed_batch) -> tuple[np.ndarray, list[Doc]]:
    sem = asyncio.Semaphore(8)
    texts = [d.text for d in docs]
    batches = [texts[i:i+64] for i in range(0, len(texts), 64)]
    out = await asyncio.gather(*(embed_batch(b, sem) for b in batches))
    vecs = np.asarray([v for b in out for v in b], dtype=np.float32)
    vecs /= np.clip(np.linalg.norm(vecs, axis=1, keepdims=True), 1e-12, None)
    return vecs, docs

# --- Stage 3: retrieve top-k by cosine (NP3) ---
def retrieve(query_vec, index, docs, k=5):
    q = query_vec / np.clip(np.linalg.norm(query_vec), 1e-12, None)
    scores = index @ q
    top = np.argpartition(-scores, k)[:k]
    top = top[np.argsort(-scores[top])]
    return [(docs[i], float(scores[i])) for i in top]

# --- Stage 4: assemble budgeted context + resilient answer (LL7/LL1/LL2) ---
def answer(client, question, hits, budget=6000):
    ctx, used = [], 0
    for doc, score in hits:
        cost = len(doc.text) // 4
        if used + cost > budget: break
        ctx.append(f"[{doc.id}] {doc.text}"); used += cost
    prompt = f"Context:\n" + "\n\n".join(ctx) + f"\n\nQuestion: {question}"
    resp = client.messages.create(model="claude-sonnet-4-6", max_tokens=500,
               messages=[{"role": "user", "content": prompt}])   # wrap w/ LL2 retry
    return resp.content[0].text
COMMON PITFALL
The most common integration bug is a silent misalignment between the vector index and its source documents — if embedding batches are flattened out of order, index[i] stops corresponding to docs[i] and retrieval returns confidently wrong chunks. Keep the index and the document list in lockstep, built from the same ordered pass.
HOW IT CONNECTS
This project is the through-line of the entire lab: every stage is a section you can now go deepen. Swap the in-memory index for a real vector store, the naive chunking for structure-aware splitting, add reranking and caching — and you have exactly the production RAG systems your other labs cover.
