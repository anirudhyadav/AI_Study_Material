F1 What MCP Is & the M×N Problem Concept Start here
The Model Context Protocol (MCP) is an open standard that gives AI applications one universal way to connect to tools, data, and prompts. It turns the M×N integration explosion into M+N: build a server once, and any compliant client can use it.
Why this matters — use case
Your refund assistant needs order data, a refund tool, and policy documents - and so does your IDE copilot, and your internal ops app. Without MCP each app wires up each tool bespoke. With MCP you build one refund server and every client speaks to it the same way.
What's in this section
  • MCP is an open JSON-RPC standard for connecting AI apps to tools, data, and prompts
  • It solves the M×N problem: M apps × N tools bespoke integrations become M+N adapters
  • Often called 'the USB-C of AI integrations' - one standard, any client to any server
  • Introduced by Anthropic in Nov 2024; donated to the Linux Foundation in Dec 2025
  • Three primitives only: tools (actions), resources (read-only data), prompts (templates)

Deep dive
Before MCP, connecting AI applications to external capabilities was an integration nightmare with a specific shape: every application that wanted to use every tool had to build a custom integration for it. With M applications and N tools, that's M×N bespoke connectors, each inventing its own auth, its own data handling, its own error conventions - and each needing maintenance as both sides evolve. MCP attacks this combinatorial explosion the same way USB-C attacked the tangle of proprietary connectors: by defining one standard interface both sides implement. A tool is exposed once as an MCP server; any MCP-compliant client can then talk to it without bespoke wiring. M×N integrations collapse to M+N adapters - M clients each speaking MCP, N servers each speaking MCP. The protocol itself is deliberately small. It's JSON-RPC 2.0 underneath, and it defines exactly three primitives a server can expose: tools (actions the model can invoke), resources (read-only data the application can pull in), and prompts (reusable templates a user can trigger). That minimalism is a feature - a small, well-specified surface is what lets thousands of independently-built servers and clients interoperate. It's worth being precise about what MCP is not: it isn't a replacement for your APIs, which still do the actual work, and it isn't an agent framework. It's the standardized connective tissue between an AI application and the capabilities it draws on. The trajectory underlines how central it's become - Anthropic introduced it in late 2024, adoption spread across OpenAI, Google, and Microsoft through 2025, and in December 2025 it was donated to the Agentic AI Foundation under the Linux Foundation, making it a vendor-neutral, community-governed standard rather than one company's project.

# Build a server ONCE; any compliant client speaks to it the same way.

# ---------------------------------------------------------------------------
# A minimal MCP server using the official Python SDK (FastMCP).
# This same server is usable by Claude Desktop, an IDE, or your own client -
# you never write per-client integration code.
# ---------------------------------------------------------------------------
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("refund-service")


# A TOOL: an action the model can invoke (more in S1)
@mcp.tool()
def issue_refund(order_id: str, amount: float) -> str:
    """Issue a refund for an order. Amount in USD."""
    # ... real logic calls your existing refund API ...
    return f"refunded ${amount:.2f} for {order_id}"


# A RESOURCE: read-only context, addressed by URI (more in S2)
@mcp.resource("policy://refunds")
def refund_policy() -> str:
    """The current refund policy document."""
    return "Refunds are eligible within 30 days... (Sec 4.2)"


# A PROMPT: a reusable template a user can trigger (more in S3)
@mcp.prompt()
def refund_review(order_id: str) -> str:
    """Template for reviewing a refund request."""
    return f"Review the refund request for order {order_id}. Check policy Sec 4.2."


if __name__ == "__main__":
    mcp.run()      # speaks JSON-RPC over stdio by default

# The point: this ONE server is consumed by MANY clients with zero
# per-client code. That is the M+N win.

F2 Architecture: Host, Client, Server Concept Foundation
MCP has three roles. The host is the AI application; inside it, one client maintains a 1:1 session to each server; each server exposes capabilities. Crucially, the host - not the protocol - owns consent, credentials, and the allow-list.
Why this matters — use case
Your host app (say, the agent platform) connects to a refund server, an orders-DB server, and a filesystem server. It spins up one client per server, keeps them isolated, and decides which tools the model may actually call - the security boundary lives in the host, by design.
What's in this section
  • Host = the AI application the user interacts with (Claude Desktop, an IDE, your app)
  • Client = a connector inside the host holding a 1:1 session to one server
  • Server = exposes tools/resources/prompts; can be local or remote
  • One client per server keeps sessions isolated and independently governed
  • Security lives in the HOST: consent, credential scope, and the per-tool allow-list

Deep dive
MCP's architecture has exactly three roles and the relationships between them matter. The host is the AI application the user actually interacts with - Claude Desktop, an IDE, or your own product - and it's the component that contains the LLM and orchestrates everything. Within the host live one or more clients, and the key rule is that each client maintains a dedicated one-to-one session with a single server. If the host connects to three servers, it runs three clients, each isolated from the others. Servers are the programs that expose capabilities - tools, resources, prompts - and a server can be a local subprocess on the same machine (a filesystem server, say) or a remote hosted service reached over HTTP. This 1:1 client-to-server pairing is deliberate: it keeps each connection independently addressable, independently authenticated, and independently governable, so a compromised or misbehaving server is contained to its own client rather than bleeding into others. The single most important architectural principle - and the one most often missed - is where security lives. It lives in the host, not in the protocol. The host owns user consent (approving that a tool may run), credential scope (what each server is allowed to access), and the allow-list (which tools the model may invoke at all). The protocol deliberately doesn't try to enforce these; it standardizes the communication and leaves the trust decisions to the host, because the host is where the user actually is and where informed consent can be obtained. This is why you can't fully evaluate an MCP deployment's safety by looking at servers alone - the host's consent and governance behaviour is half the picture, and in an enterprise you often concentrate that behaviour in a gateway (see the capstone, P2).

# Three roles: HOST (the app + LLM) -> CLIENTs (1:1 sessions) -> SERVERs.
# The HOST owns consent, credentials, and the allow-list - not the protocol.

import asyncio
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client


# ---------------------------------------------------------------------------
# A host connects to MULTIPLE servers - one CLIENT session each (1:1).
# ---------------------------------------------------------------------------
SERVERS = {
    "refunds":   StdioServerParameters(command="python", args=["refund_server.py"]),
    "orders":    StdioServerParameters(command="python", args=["orders_server.py"]),
    "filesystem":StdioServerParameters(command="npx", args=["-y", "@modelcontextprotocol/server-filesystem", "/data"]),
}

# The host's security policy - THIS is where trust decisions live:
ALLOW_LIST = {
    "refunds":    {"issue_refund", "get_refund_status"},   # explicitly allowed tools
    "orders":     {"lookup_order"},                        # read-only only
    "filesystem": {"read_file"},                           # NOT write_file / delete
}

async def call_if_allowed(server_name: str, session: ClientSession,
                          tool: str, args: dict):
    # host-side gate: the model can only reach allow-listed tools
    if tool not in ALLOW_LIST.get(server_name, set()):
        raise PermissionError(f"host blocks {server_name}.{tool}")
    # (a real host also asks the USER to consent to side-effecting calls)
    return await session.call_tool(tool, args)


async def connect(server_name: str):
    params = SERVERS[server_name]
    async with stdio_client(params) as (read, write):
        async with ClientSession(read, write) as session:   # one client : one server
            await session.initialize()
            tools = await session.list_tools()
            print(f"[{server_name}] offers:", [t.name for t in tools.tools])
            return session


# each server gets its OWN isolated client session:
async def main():
    await connect("refunds")     # isolated
    await connect("orders")      # isolated
    # a misbehaving server is contained to its own client

F3 JSON-RPC & the Lifecycle Handshake Protocol Internals
Under the hood MCP is JSON-RPC 2.0: request/response pairs and one-way notifications. Every session opens with an initialize handshake that negotiates protocol version and capabilities, so each side only uses what the other supports.
Why this matters — use case
When your client connects to the refund server, the very first exchange is initialize: they agree on a protocol version and each declares what it supports. Only after that does the client list tools and start calling them - the handshake is what makes version mismatches graceful.
What's in this section
  • MCP messages are JSON-RPC 2.0: requests (with an id) get responses; notifications don't
  • Every session starts with initialize - the client sends version + capabilities
  • The server replies with its capabilities; the client sends notifications/initialized
  • Capability negotiation means each side only calls features the other advertised
  • The spec is date-versioned (2025-11-25 stable; 2026-07-28 RC makes the core stateless)

Deep dive
Underneath the primitives, MCP is JSON-RPC 2.0, and understanding that wire format demystifies everything above it. JSON-RPC has two message shapes: a request carries a method name, params, and an id, and expects a matching response with that id; a notification carries a method and params but no id and expects no reply - it's fire-and-forget, used for lifecycle signals and dynamic updates. Every MCP interaction is one of these frames, whether it travels over stdio or HTTP. The session always begins with a specific choreography called the initialize handshake. The client sends an initialize request declaring the protocol version it speaks and the capabilities it offers (things like sampling, roots, elicitation). The server responds with its own capabilities - which of tools, resources, and prompts it exposes, and whether it supports dynamic list changes. The client then sends a notifications/initialized notification to signal it's ready, and only now does normal operation begin: tools/list to discover tools, tools/call to invoke one, resources/read to pull data, and so on. This up-front capability negotiation is what makes MCP robust across versions and implementations - because each side has explicitly told the other what it supports, neither calls a feature the other can't handle, and an old client talking to a new server simply uses the common subset. MCP's versioning reinforces this: the spec is date-stamped (2025-11-25 is a stable release; the 2026-07-28 release candidate makes the core protocol stateless), and version negotiation in the handshake lets old and new implementations interoperate rather than breaking. One notable direction of travel: the newer stateless model leans on the model threading explicit identifiers between calls rather than the protocol holding hidden session state, which turns out to compose better and scales more cleanly behind load balancers.

# MCP is JSON-RPC 2.0 underneath. Every session opens with an initialize
# handshake that negotiates version + capabilities BEFORE any real calls.

# ---------------------------------------------------------------------------
# What the wire actually looks like (JSON-RPC 2.0 frames)
# ---------------------------------------------------------------------------
INITIALIZE_REQUEST = {           # request: has an id, expects a response
    "jsonrpc": "2.0",
    "id": 1,
    "method": "initialize",
    "params": {
        "protocolVersion": "2025-11-25",
        "capabilities": {                     # what the CLIENT offers
            "sampling": {},
            "roots": {"listChanged": True},
            "elicitation": {},
        },
        "clientInfo": {"name": "refund-host", "version": "1.0"},
    },
}

INITIALIZE_RESPONSE = {          # response: same id, server's capabilities
    "jsonrpc": "2.0",
    "id": 1,
    "result": {
        "protocolVersion": "2025-11-25",
        "capabilities": {                     # what the SERVER offers
            "tools": {"listChanged": True},
            "resources": {"subscribe": True},
            "prompts": {},
        },
        "serverInfo": {"name": "refund-service", "version": "2.1"},
    },
}

INITIALIZED_NOTIFICATION = {     # notification: NO id, no response expected
    "jsonrpc": "2.0",
    "method": "notifications/initialized",
}

# ---------------------------------------------------------------------------

from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

async def main():
    params = StdioServerParameters(command="python", args=["refund_server.py"])
    async with stdio_client(params) as (read, write):
        async with ClientSession(read, write) as session:
            init_result = await session.initialize()      # the whole handshake

            caps = init_result.capabilities
            # only use what the SERVER advertised (don't assume):
            if caps.tools is not None:
                tools = await session.list_tools()         # method: tools/list
                result = await session.call_tool(          # method: tools/call
                    "issue_refund", {"order_id": "ORD-1", "amount": 50.0})
            if caps.resources is not None:
                await session.list_resources()             # resources/list

S1 Tools — Model-Invoked Actions Primitive Most used
Tools are the actions an MCP server exposes for the model to invoke. Each has a name, a description, and a JSON Schema for its inputs. Because the MODEL chooses when to call them, the description is effectively part of the prompt.
Why this matters — use case
Your refund server exposes issue_refund(order_id, amount) and get_refund_status(order_id). The model reads their descriptions, decides which fits the user's request, and calls it with arguments. Clear, precise descriptions are what make the model call the right tool correctly.

  • Discovered via tools/list, invoked via tools/call - both standard methods

Concept diagram
Deep dive
Tools are the most-used MCP primitive because they're how a model actually does things rather than just reads things. A tool is defined by three parts: a name, a natural-language description, and a JSON Schema describing its input parameters (and, since the 2025-06-18 revision, optionally its structured output). The client discovers available tools with tools/list and invokes one with tools/call, passing the tool name and an arguments object that conforms to the schema. The defining characteristic of tools - the thing that shapes how you design them - is that the model chooses when to call them. Unlike resources (which the application pulls) or prompts (which the user triggers), a tool fires because the model, reading the available tools and their descriptions, decides one is appropriate for the current task. This has a profound practical consequence: the tool's description is not documentation, it's prompt. The quality of that description directly determines whether the model picks the right tool at the right time with the right arguments. A vague description ('handles refunds') invites misuse; a precise one ('Issue a monetary refund for a specific order. Use only after confirming eligibility. amount is in USD.') steers the model correctly. The input schema does double duty - it tells the model how to shape arguments and it validates what comes back before your code runs. The final design axis is safety. Because tools take actions and the model invokes them autonomously, side-effecting tools (issuing refunds, deleting data, sending messages) are exactly where host consent belongs: the host should gate their execution behind an allow-list and, for consequential actions, explicit user approval. This is the precise point where MCP and human-in-the-loop meet - the tool is the action, and the host is the gate.
python s1_tools.py
# Tools = model-invoked ACTIONS. name + description + input schema.
# The MODEL decides when to call them, so the DESCRIPTION is prompt-critical.

from mcp.server.fastmcp import FastMCP
from pydantic import Field
from typing import Annotated

mcp = FastMCP("refund-service")


# ---------------------------------------------------------------------------
# GOOD tool: precise description (the model reads this to decide) + typed args
# ---------------------------------------------------------------------------
@mcp.tool()
def issue_refund(
    order_id: Annotated[str, Field(description="The order to refund, e.g. 'ORD-8891'")],
    amount: Annotated[float, Field(gt=0, le=10000, description="Refund amount in USD")],
) -> str:
    """Issue a monetary refund for a specific order.

    Use ONLY after confirming the order is refund-eligible under policy.
    Do NOT use for status questions - use get_refund_status for those.
    'amount' is the refund value in USD, not the order total.
    """
    # side effect -> the HOST should gate this behind user consent
    return f"Refunded ${amount:.2f} for {order_id}"


# a read-only tool the model can call freely
@mcp.tool()
def get_refund_status(
    order_id: Annotated[str, Field(description="The order to check")],
) -> str:
    """Return the current refund status for an order. Read-only, safe to call."""
    return f"{order_id}: refund pending review"

# BAD tool (for contrast) - vague description invites misuse:
#   @mcp.tool()

#       ...
# ---------------------------------------------------------------------------

if __name__ == "__main__":
    mcp.run()

Deep dive
Resources are MCP's answer to 'how does the model get read-only context', and the crucial thing that distinguishes them from tools is control. A tool is model-controlled - the model decides to call it. A resource is application-controlled - the host decides to pull it into context. Deep dive
MCP separates the message format from the transport that carries it, so the same JSON-RPC 2.0 payloads run over either of two transports, chosen by deployment shape. The stdio transport runs the server as a local subprocess of the host and exchanges messages over standard input and output. This is what lets you develop a server locally over stdio and deploy the identical logic as a remote HTTP service. One direction worth noting: the 2026 release-candidate spec makes the HTTP transport stateless, removing protocol-level sessions in favor of the model threading explicit handles between calls, which composes better behind load balancers and gateways - relevant when you scale a remote server horizontally.

Deep dive
Security is where MCP got serious as it moved from local experiments to remote, internet-facing deployments, and the headline rule is unambiguous: any MCP server reachable over the internet must implement OAuth 2.1 with PKCE, and this has been mandatory since the 2025-03-26 revision. (stdio servers, being local, are exempt and take credentials from the environment instead.) The architecture OAuth 2.1 imposes is the important part. It separates the token issuer from the resource server: an authorization server (your identity provider) issues tokens, and the MCP server acts purely as an OAuth 2.1 resource server that validates them. This separation is what turns credential management from a sprawl of permanent secrets into an auditable system of short-lived, scoped tokens - a client proves its identity through the Authorization Code flow with PKCE (the S256 method), receives a token scoped to just what it needs, and that token expires. Several hardening requirements sit on top. Audience validation via Resource Indicators (RFC 8707) means a token is bound to the specific server it was issued for, so a token meant for one resource can't be replayed against another - a real concern in MCP's single-client, many-server world. Protected Resource Metadata (RFC 9728) lets clients discover the right authorization server for a given resource. And a specific anti-pattern is explicitly banned: token passthrough, where an MCP server takes a token a client gave it and forwards it, unvalidated, to a downstream external API. When an MCP server needs to call an external service (GitHub, Slack, a payment API), it must obtain its own properly-scoped credentials for that service - not launder the client's token. The practical reality is sobering: surveys have found only a small fraction of public MCP servers actually implement the mandated OAuth, so the security gap in the ecosystem is wide, and for anything handling sensitive or enterprise data, closing it is the difference between an auditable access-control system and a credential nightmare. The 2026 spec further hardens this with issuer validation (RFC 9207) to blunt mix-up attacks.

The 2026 spec's operational headers (routing on method and name without inspecting the body) exist precisely to make this gateway pattern efficient. Behind the gateway sits a registry of servers that are registered and versioned rather than ad-hoc endpoints - which is what lets an organization know what MCP surface it actually exposes, review new servers before they're reachable, and manage version changes deliberately. Several earlier threads converge here. The host-owned allow-list and consent (F2) become gateway policy. Roots-style scoping (C3) becomes centrally-enforced per-server access. OAuth 2.1 (P1) becomes a gateway responsibility rather than something each server implements independently, which also fixes the ecosystem's low OAuth-adoption problem inside your own walls. The stateless direction of the 2026 transport (S4) matters at this scale because it removes session affinity, letting servers behind the gateway scale horizontally without sticky routing. The governance payoff is the ability to answer, at any moment, what tools exist, who can call them, who did call them, and under what authority - which is the baseline a regulated enterprise needs before it can trust autonomous agents with real actions. As with the host model throughout, the protocol gives you the mechanisms; the gateway and registry are the organizational discipline that turns those mechanisms into governance.

# Enterprise MCP: a GATEWAY centralizes what F2 says each host must do -
# OAuth, allow-list, scope, audit, rate-limit - across a REGISTRY of servers.

from dataclasses import dataclass, field
from datetime import datetime, timezone


# ---------------------------------------------------------------------------
# A registry of REGISTERED, VERSIONED servers (not ad-hoc endpoints)
# ---------------------------------------------------------------------------
@dataclass
class RegisteredServer:
    name: str
    version: str
    url: str
    allowed_scopes: set[str]              # what THIS server may be granted

REGISTRY = {
    "refunds":  RegisteredServer("refunds", "2.1", "https://mcp.int/refunds",  {"refunds:write", "refunds:read"}),
    "orders":   RegisteredServer("orders",  "1.4", "https://mcp.int/orders",   {"orders:read"}),
    "policy":   RegisteredServer("policy",  "1.0", "https://mcp.int/policy",   {"policy:read"}),
}

# per-HOST entitlements - enforced centrally, not reimplemented per host
HOST_ENTITLEMENTS = {
    "agent-platform": {"refunds:read", "orders:read", "policy:read"},
    "ops-console":    {"refunds:write", "refunds:read", "orders:read", "policy:read"},
    "ide-copilots":   {"policy:read"},
}


# ---------------------------------------------------------------------------
# The gateway: one governed path between every host and every server
# ---------------------------------------------------------------------------
class MCPGateway:
    def __init__(self):
        self.audit: list[dict] = []

    def route_call(self, host: str, server: str, tool: str,
                   scope: str, token) -> str:
        # 1. OAuth 2.1: validate token (audience, expiry, signature) - central
        self._validate_token(token, audience=REGISTRY[server].url)

        # 2. allow-list / scope: is this host entitled to this scope?
        if scope not in HOST_ENTITLEMENTS.get(host, set()):
            self._log(host, server, tool, scope, "DENIED: not entitled")
            raise PermissionError(f"{host} lacks {scope}")

        # 3. scope must be one the server even accepts (least privilege)
        if scope not in REGISTRY[server].allowed_scopes:
            raise PermissionError(f"{server} does not grant {scope}")

        # 4. (rate-limit / route here) ... then forward to the server
        result = self._forward(server, tool)

        # 5. audit: who called what, with what scope, when
        self._log(host, server, tool, scope, "OK")
        return result

    def _forward(self, server, tool): return f"{server}.{tool} -> ok"
    def _log(self, host, server, tool, scope, outcome):
        self.audit.append({
            "ts": datetime.now(timezone.utc).isoformat(),
            "host": host, "server": server, "tool": tool,
            "scope": scope, "outcome": outcome,
        })

⚑ Real-world scenario
An enterprise had MCP adoption spreading organically - several teams had stood up servers, and several AI surfaces were consuming them, each handling auth and access its own way. A risk review found the predictable problems: inconsistent OAuth (some servers had none), no central record of which agent had called which tool, and no way to enumerate the full MCP surface the company exposed. They introduced a gateway as the single path between hosts and servers. It centralized OAuth 2.1 and token validation, enforced per-host allow-lists and per-server scope, and logged every tool call with its identity, scope, and timestamp to an audit store. Servers had to be registered and versioned to sit behind it, giving the organization a reviewable inventory. When a new third-party server was proposed, it went through registration and scoping before any host could reach it. The company could finally answer the governance questions - what exists, who can call it, who did - that a regulated environment requires, and the stateless transport let the busy servers scale out behind the gateway without sticky sessions.

Because the host-owned security model, while correct, doesn't scale when dozens of hosts each reimplement OAuth, allow-listing, and audit - you get inconsistency and gaps. Centralize through a gateway and a registry before the sprawl outruns your ability to govern it.
